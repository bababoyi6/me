# 入口共享预算：单变量执行前登记

前阶段仅后端180Mbps：回程路由采样峰值约6.2→1.2MB，但入口发送方向峰值约0.35–0.45→2.18–2.68MB；该方向多出的排队可能解释部分新连接尾延迟。CPU平均各进程均低于8%，尚无CPU饥饿证据。此为同一任务的观察，不把netem传播持包全部算为多余排队，也不将所有延迟归因于入口。

本次最小候选是**只在隔离CI**将入口两条独立WG的明文egress重定向至同一个内核IFB，HTB180Mbps+fq_codel处理后重注入原WG。每条隧道的密钥/路由保持，根qdisc不改，物理接口/SSH/全局防火墙不接管。没有新增隧道、协议层或守护进程；新增一个内核排队接口/clsact也有额外开销和生命周期成本，先验证再决定是否值得接入。

官方Linux5.15源码[IFB](https://github.com/torvalds/linux/blob/v5.15/drivers/net/ifb.c)说明其用途包含跨设备共享队列，并按原ifindex重新注入egress；[WireGuard send.c](https://github.com/torvalds/linux/blob/v5.15/drivers/net/wireguard/send.c)在加密前计算内层流hash。这里直接在加密前分类，不依赖公网路径保留hash。源码分析不是性能证明。

先运行不依赖Telemt的双真实WG功能检查：两路共同总预算150–185Mbps、每路>40Mbps；一路空闲时另一条>150Mbps，避免静态均分浪费；单个后端隧道故障不影响另一条；重复启用不重置、正常撤销恢复根队列/删除IFB、密钥不变和清理/OOM。iperf双向统一接收端本地计量，完整原始JSON保留。这只证明两个私有WG的预算/转发，不声称双后端完整Telegram业务。

前置成功后只做一次固定原生17、100ms/200Mbps/30逻辑混合、四对AB/BA：**两臂均开启相同后端180Mbps策略**；变量仅是入口共享IFB开/关。复用固定二进制、3CPU/1.5GiB/无swap和原分析器；预登记门槛仍为每对上下行≥95%、两类满载p95≤基线90%且≤空载+100ms、RSS/整组CPU秒≤110%、两类满载样本≥20、双向本地容量≥100Mbps、完整性全通过、OOM0及清理完成。全部原始成功/失败保留。任一失败不改参数/门槛找赢家，不进入默认生产配置。

这里只改变测试原型，生产管理器保持d0c6b90的默认关闭后端实验，不开放入口启用。即使本场景通过，也不能代替独立backend2协议、共享公网瓶颈、1Gbps、ARM、完整重启、真实客户端、三VPS、24小时或抗封锁验收。Linux只GitHub有界CI，不访问VPS、不本地Linux执行或购买资源。结果待真实运行补齐。
