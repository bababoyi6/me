# 1.7 故障排查

> 11月9日更新：当前目标3.5.17；最新官方退化复现、原生移植、队列负面结果、同负载与资源分位数见[最终验收报告](FINAL-ACCEPTANCE-20261109.md)。下文3.5.16数据保留原历史口径，不能替代新版验收。

先用 `a status`、`a diagnose`、`a perf 5` 收集脱敏观察。`a links`、`state.env`、WG 配置、API 令牌、加入码及回执均含凭据，不贴到公共日志。以下操作必须在获准维护的节点上执行，本轮没有执行生产命令。

| 现象 | 定位顺序 | 恢复方式/边界 |
|---|---|---|
| 高延迟单流吞吐下降，但 CPU 不高 | 核对实际核心、WG RTT 与 TCP 的 rb/tb；3.5.16 固定缓冲在 100ms 实验出现明显限制 | 参考长链路报告，保留旧核心回退；不要用更换 Secret 或盲目放大 sysctl 处理。原生移植仍是未发布候选，四流排队延迟待优化 |
| 只有一条线路失败 | 比较 SNI、对应主后端和备用后端状态；保留原 Secret | 不重生成链接；对问题后端单独排空维护 |
| 单个 DC TCP 不通 | 查看五个 DC 的逐个诊断；多数票可能仍为 UP | UP 不证明每个 DC 正常，不能把多数票解释为全部成功 |
| connect-refresh 提示配置或备份上限 | 查看是否超过 1MiB 或已保留 8 份不同基线备份；服务尚未停止 | 先在 root 私有位置审查/归档未引用备份；不要移动当前事务及 prior 引用的备份，不要直接删除恢复资料 |
| 认证成功、负载前关闭，日志为 DC Connection timeout | 核对实际 DC 路径与 `upstream_connect_budget_ms`，原默认总预算仅 3 秒 | 新版的 `connect-refresh --maintenance` 可应用有界重试；先排空后端并备份，定制值需审查，不重生成 Secret |
| 核心在、代理为 down | 本机 API 就绪、WG 监听端口、DC 多数、样本新鲜度、恢复冷却 | 新健康代理冷启动至少约 20 秒；真实超时会增加等待 |
| 健康代理退出 | 查看代理单元状态及重启计数 | systemd 自动重启；HAProxy 对代理端口的检查防止永久假 UP |
| 健康代理报 health monitor progress deadline | 检查本机API是否零星返回但迟迟不能完成、DC探测是否有进展；不要公开API令牌或原配置 | 新版15/45秒整轮进度保护会只重启健康代理，普通不健康票不触发；需反复恢复时排空该后端并查API/资源原因，不关闭保护或循环重启Telemt |
| 两条线路都断 | 入口监听、HAProxy、两个 WG 握手、两个后端健康 | 两后端均失效没有第三个代理；Apple 伪装回落不能转发 MTProto |
| WG 数据面短断 | 比较握手时间与 RX/TX，检查对端 UDP 和路径 MTU | 链路恢复后允许重握手；原连接可能超时并重连 |
| 手动 stop WG 后核心未重启 | `Requires=` 可能已停掉依赖 | 在该后端运行 `a recover`，再检查入口状态 |
| 核心升级预检失败 | 包摘要、非特权 `--version`、旧配置严格解析、当前 API、MainPID 身份 | 服务尚未替换；不要重新初始化节点 |
| 新核心安装时反复退出、API 不通且报 Permission denied | 核对配置父目录；上游安全读取需要目录的读及搜索权限 | 托管新安装使用 root:telemt 0750；旧节点由核心维护事务迁移，勿放开密钥/状态文件权限，详见升级文档 |
| 核心替换后恢复失败 | 保留入口 drain，检查事务阶段和旧二进制摘要 | `a core-rollback --maintenance`；不删除 transaction.json 或旧核心 |
| 回退报告配置变化 | 对比私有快照的哈希/权限/文件集合、专用 drop-in | 停止自动覆盖，由维护者决定是否恢复旧配置 |
| 临时实验启动慢 | 隔离网络没有外部 DNS/STUN、TLS front 无缓存 | 测试专用 offline bootstrap 关闭外部采样；不得把它当生产优化 |
| 新安装下载 403/404 | 仓库可见性、Release 资产和认证条件 | 不使用 main 或其他未知二进制回退；重新核对正式固定下载 |

审计核心包的私有留档若提示篡改/不安全链接/8份上限，会在停服务前拒绝；保留当前事务及被引用的恢复资料，先由root审查归档，不直接清空目录。该低层审计模式不等于已开放生产优化核心选项。重复相同核心时也会复核对应归档，业务无需为补存资料而重启。

满载RTT升高应同时核对旧版基线、实际吞吐、独立探测丢失和路由队列；本轮确认旧balanced2也会排队。不能因为缩小模型队列后收到的ping更快，就忽略同时出现的丢失/吞吐下降。[本轮补验](NATIVE-QUALIFICATION-20261109.md)。

默认内核/HAProxy参数未因核心升级重新应用。先核对实际 socket、RTT、重传和队列，再决定调 MTU/MSS/缓冲；不要复制全局防火墙清空、无限重试或激进 sysctl 命令。

iperf低读数也要先检查计量窗口：Ubuntu22.04内置3.9在本次上行实验中出现发送6秒、远端接收汇总16秒，183Mbps传输被显示为69Mbps。不要改用较高发送值来宣布链路通过；本轮工具用两个方向的本地接收计量并核对时间/字节，旧失败记录保留。旧netem吞吐脚本的历史远端汇总也不能脱离完整JSON单独作为容量结论。HTB的旧版tc统计可能混入非JSON文本，诊断保留原始文本，不截掉异常部分。[证据和限定范围](PATH-CAPACITY-20261109.md)。

健康代理只做 API、端口和 TCP 多数探测。官方客户端授权、Telegram 文件传输、移动网络 Carrier、跨运营商和抗识别能力需要独立业务证据。短时 FD 回落不能证明长期没有内存泄漏，56 分钟历史记录不能证明 24 小时稳定。
