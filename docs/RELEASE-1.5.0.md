# 1.5.0：新安装默认后端修复，公开实测收益与取舍

本版解决两个经过源码和传输实验复现的后端问题：加密写入尾部可能在等待新输入时未被继续flush；显式固定TCP收发缓冲限制高RTT单连接吞吐。Ubuntu22.04 x86_64首次安装默认采用非官方`3.5.5+tdh.audit2`，不需要事后开启提速参数，不在1GB节点现场编译。它是基于官方3.5.5的六文件最小修改，保留原依赖锁、许可、密码算法、认证、协议及访问控制，不能称为Telemt官方发布。

## 已落地的变化

- 后端：补齐Direct自适应复制在源读取Pending时的flush推进，保留部分写、背压、EOF和错误传播；取消client及Direct outgoing socket的固定256KiB收发请求，交由Linux自动缓冲。fallback socket策略和用户态复制预算不变。
- 新安装：脚本内嵌安全安装器，先验证固定归档摘要，再验证核心、清单、架构和版本；拒绝目录穿越、链接、重复/多余成员和超限数据，以telemt身份检查版本后排他安装。保留许可、源码补丁及构建记录，校验失败停止并清理安装事务。
- 安装可靠性：在软件包安装、加入码提示和事务写入前拒绝已有同名项目路径，避免失败清理误删预存内容；一键命令有下载期限、大小/协议检查、项目标识、语法检查和独立临时文件清理。
- 维护与诊断：加固维护锁和异常退出恢复；`a perf 5`提供只读脱敏采样，不上传凭据、不启动负载。保留原有`a update`管理器维护及回退边界。
- 证据与回归：补充真实HAProxy、加密MTProto合成传输、持久连接尾部、隔离安装恢复及核心flush回归；保存成功、失败及每轮原始记录。

两条SNI、WireGuard+PSK、Direct-DC、fast_mode、BBR/fq、双后端主备、API本地绑定及现有访问控制保留。没有更换内核、默认强制splice、全局堆叠缓冲参数或调整生产NIC offload。ARM继续使用校验固定归档的官方3.5.5，没有ARM提速构建或执行验收。

## 可量化的突破

所有数字来自获授权的一台荷兰1核1GB临时Ubuntu22.04测试机的受控实验，不是生产三机或真实Telegram文件测速。

| 条件与指标 | 对照 | audit2 |
|---|---:|---:|
| 100ms/100Mbps，完整WG+PSK双后端路径，单流16MiB下载3轮中位数 | 官方3.5.5：22.745Mbps | 55.915Mbps |
| 100ms/1000Mbps预算，原始DC TCP段，单流64MiB下载3轮中位数 | audit1：16.146Mbps | 156.682Mbps |
| 同上上传 | audit1：23.044Mbps | 169.434Mbps |
| 100ms/1000Mbps预算，32并发×8MiB上传，交换版本顺序后3轮中位数 | audit1：375.806Mbps | 273.477Mbps |

audit1已经包含flush修复，仍固定socket缓冲；后面三项不能称为未经修改官方版本的对照。第一项显示完整WG合成路径下约2.46倍下载收益；单连接大幅改善说明软件窗口限制确实存在，但32并发上传约27%回退也得到复验。不得只选有利样本或宣传全场景提速。

官方版本的一类上传尾部不完整在原生实验中被复现，flush修复后相关持久连接与完整性回归通过；这不证明所有尾部问题都已解决。自动缓冲可能增加内核socket内存，进程RSS近似不变不能证明总内存成本相同。

一次32并发慢读初测有4条下载提前结束，模拟DC记录4次payload阶段8秒socket超时。仅将模拟DC期限改为25秒后，多轮和后续观察共768条大流校验成功、无OOM；没有调整生产服务超时。并发回退的完整成因仍未知：追加观察显示自动缓冲组重传计数较高，中间netem及两端fq未记录丢包，不能将其归因为公网线路，也不能证明是单纯排队丢包。

原始记录及方法见[新安装验收](FRESH-INSTALL-1.5.0.md)、[1Gbps预算数值汇总](benchmarks/native-1g-summary.json)、[后端源码与对照](NATIVE-BACKEND-VALIDATION.md)、[完整WG逐轮结果](benchmarks/native-dualhop-auto-benchmark.json)。

## 已验证的稳定性范围

本机Linux与原生Ubuntu22.04的129项Python回归、Bash语法、ShellCheck、内置自测通过；原生真实HAProxy分流、PROXYv2、完整字节和agent切换检查，以及27个隔离安装恢复场景通过。

三套Ubuntu22.04/systemd测试节点使用同一条README命令完成入口/两后端安装，验证坏归档拒绝后重试、预存目录保护、实际停主后端后的新连接切备、恢复及正常关机再启动。两后端默认核心摘要一致；重启后13/16/16份受保护文件保持原字节，双SNI真实Telegram DC公开握手继续通过。三套guest共用一台宿主、软件包和测试内核此前准备，不能冒称三台独立生产VPS容量或全新出厂镜像验收。

另有约10分钟持续传输、慢读并发和小文件探测的178次完整校验，见[核心资源验收](CORE-ENABLEMENT-VALIDATION.md)。这不等于数天长期满载验证。切备不迁移已有TCP会话；连接接入上限不等于同等数量满速大流容量。没有生产访问、真实Telegram账号/文件或洛杉矶/纽约公网容量数据，不承诺零bug、永久无需维护或1Gbps跑满。

## 安装、现有节点与发布产物

三台分别执行[README的一键命令](../README.md)，选择角色并交换加入码/回执即可生成配置。x86_64新后端默认audit2，无需额外提速开关。

`a update`及重复安装命令只维护已有管理器，不替换运行核心、不重建配置或重新生成连接信息。本版的核心默认值面向新安装；运行`a update`不能据此宣称既有生产已获得核心提速。本轮没有新增生产无损轮换机制。
