# 分离负载端的长链路实验（2026-11-08）

> 11月9日更新：当前目标3.5.17；最新官方退化复现、原生移植、队列负面结果、同负载与资源分位数见[最终验收报告](FINAL-ACCEPTANCE-20261109.md)。下文3.5.16数据保留原历史口径，不能替代新版验收。

本轮只改测试工具，不更换候选的官方 3.5.16 核心或生产默认参数。前一轮持续组受 Python 生成器限制，不能用它判断核心吞吐上限，因此补充以下实验。

## 方法与事先门槛

- 免费 Ubuntu 22.04 GitHub runner，三个私有网络命名空间、真实 WireGuard 和 HAProxy PROXY v2；入口到后端设置 0/100ms RTT、200Mbps。客户端、模拟 DC、Telemt 为独立进程，分别固定逻辑 CPU，Telemt 全部线程限一核。总预算三核、1.5GiB、无 swap、900 秒。
- 对照精确摘要锁定的 `3.5.5+tdh.balanced2`、官方 `3.5.16`，另设 `stable-auto` 因果实验：仅对模拟 DC 环境中的新版 Telemt 注入实验库，略过固定 256KiB 的收发缓冲设置。它不是生产核心，也不等同于完整移植旧版的 lowat/缓冲策略；严禁部署该实验库。
- 每条件三个循环轮次，轮换三个核心顺序；每轮单流/四流、上传/下载各 32MiB/流。合计 72 批、180 条计量流，另有 72 条双 SNI 的 4KiB 预热。真实 Fake TLS、原生代理认证、SHA/ACK 验证，DC 与内容均为模拟。
- 记录 TCP 实际 RTT/缓冲、每个进程 CPU、后端 RSS、单核绑定、传输完整性、DC 完成计数、OOM 与清理。另测每条件双向 iperf3 单流，确认路径容量。
- 分析拒绝缺批、重复、失败、配置漂移、缺少 RTT/CPU、核心绑定变化或未清理的结果。前端总 CPU 或 DC CPU 达 70% 标记生成端受限；TCP 基线不足 100Mbps 标记路径受限；100ms 条件的逐批 RTT 中位数须在 80–200ms，低延迟须小于 20ms。
- 仅当同主机三轮的候选/参考吞吐比全部大于 1.10，才标记探索性重复增益；全部小于 0.90 标记减速。不能由此推断总体统计显著性。若出现值得移植的增益，必须再由独立任务复验，并验证原生核心构建、功能和回退后再决定。

## 复现与边界

在开发分支运行 `.github/workflows/long-path.yml`，读取 `long-path-evidence/metrics.json`，以 `python3 tests/long_path_analysis.py metrics.json analysis.json` 分析。负载全部在 GitHub runner 内部产生，不经过用户本地或任何 VPS；本地仅下载压缩结果。

首轮 `42454547596` 因父进程位于宿主网络区、观测函数严格拒绝跨区采样而停止。修复为由后端区内的工作进程采集，不放宽观测权限边界；失败记录保留。

## 第一组真实结果

[42455075515](https://github.com/bababoyi6/me/actions/runs/42455075515)，测量源码 `d041ab9ae3b676b0161b8d44416cb2a056b48dff`，AMD EPYC 7763。72 批、180 条计量流与 72 条预热全部 SHA/ACK 通过；DC 完成 252 条、0 错误；OOM 为 0，进程、命名空间清理通过，最终私有 cgroup 仅控制进程一个 PID。总 cgroup 峰值 285MiB，包含测试各组件与内核计费内存，不能仅用核心 RSS 估算 socket 成本。

| 条件 | balanced2 中位 Mbps | 官方 3.5.16 中位 Mbps | stable-auto 中位 Mbps | 判定 |
|---|---:|---:|---:|---|
| 0ms 单流上传/下载 | 180.59 / 175.59 | 180.71 / 175.84 | 181.19 / 175.02 | 未见明确变化 |
| 0ms 四流上传/下载 | 182.45 / 181.18 | 182.49 / 181.16 | 182.39 / 181.25 | 未见明确变化 |
| 100ms 单流下载 | 105.17 | 21.18 | 106.00 | 新版重复减速；自动缓冲实验重复恢复 |

100ms 单流下载满足预登记 RTT、CPU、路径基线门槛；自动缓冲/官方的三轮中位比值约 5.00。100ms 上传 TCP 基线仅 53.33Mbps，四流下载部分实测 RTT 超过预登记范围；这些条件分别保留 `PATH_CONTROL_LIMITED` / `RTT_NOT_ESTABLISHED`，不据此给出提速结论，不事后放宽门槛。

实测高延迟接收缓冲：官方固定约 512KiB，自动策略增长到约 6MiB；发送缓冲也有明显差异。它们是内核限额，不等于实时分配内存。低延迟下各版接近 200Mbps 路径的有效吞吐上限，不能据此推断 1Gbps 生产上限。

## 原生移植候选的后续门槛

新增 `tools/build_stable_candidate.py`，只从锁定的官方 commit 构建同一 Rust 1.99.1 / thin LTO / 8 codegen-units 的控制版与 `3.5.16+tdh.balanced1`。候选仅在 Linux 的客户端/Direct 出站 socket 复用原有 `low_rtt_receive.rs` 与 `unsent_queue_bulk.rs`：保留自动缓冲、短 RTT 接收保护、256KiB 待发送数据限额。通用 socket、非 Linux 回退、认证、加密、Fake TLS、relay flush 均保持上游实现。

候选构建会执行上游真实 socket 测试和新增内核断言；独立测量任务使用四轮平衡 AB/BA、100ms、单流/四流上传/下载，同一套完整性与资源门槛，不使用预加载库。原生任务 TCP 基线延长为 8 秒、忽略前 3 秒，独立记录，不覆盖第一组较短控制测量。另执行 30/50/100 并发 SHA/ACK 协议回归。

生产默认仍为官方核心，实验候选不能通过管理器自动安装，构建产物只作审查。原生协议、有限资源与核心事务验收结果见下文；高延迟百流、双后端等仍未运行，排队延迟问题仍阻止直接发布为生产修复。

## 独立任务复验与原生候选结果

[42456173136](https://github.com/bababoyi6/me/actions/runs/42456173136)，源码 `b8072f319d857cdf8faec008e23b4509a988298a`，Intel Xeon Platinum 8573C，再次完成全部 72 批、180 条计量流与 72 条预热，0 错误、OOM 为 0，进程和网络区清理通过。100ms 单流下载为 balanced2 **105.31Mbps**、官方 **21.34Mbps**、自动缓冲实验 **106.09Mbps**，与第一台 AMD 主机重复；总 cgroup 峰值 293.26MiB。两个任务总计 360 条计量流，不合并不同主机的绝对速度。低延迟仍未见明确变化，上传控制与四流下载继续按原门槛标记受限。

[原生构建与测量 42456468710](https://github.com/bababoyi6/me/actions/runs/42456468710)，源码 `6dd5c4af9b0495f21d5b5b230630ed31077d7477`，AMD EPYC 7763。控制版 socket 测试 12 项通过、候选 14 项通过，各保留上游一个默认忽略的手动描述符压力测试；其余 2747 项上游测试未运行，不称全套上游测试通过。新增的实际 `SO_SNDBUF`、`SO_RCVBUF`、`TCP_NOTSENT_LOWAT` 和客户端自动发送断言通过。

| 100ms 原生同编译器配对 | 控制版中位 Mbps | balanced1 中位 Mbps | 四轮比值中位数 | 结论 |
|---|---:|---:|---:|---|
| 单流上传 | 22.97 | 105.33 | 4.58 | 符合预登记增益门槛 |
| 单流下载 | 21.07 | 105.57 | 5.00 | 符合预登记增益门槛 |
| 四流上传 | 89.68 | 153.54 | 1.71 | 符合预登记增益门槛 |
| 四流下载 | 84.16 | 158.03 | 1.88 | 实际 RTT 超过门槛，不能判定有效增益 |

原生实验 32 批、80 条计量流加 32 条预热全部 SHA/ACK 通过，DC 完成计数吻合，OOM 为 0，完整清理；总 cgroup 峰值 266.23MiB。随后两原生核心合计 **720 条** 30/50/100 并发协议负载通过。后者是 256KiB/流的有界功能回归，不是持续吞吐或用户文件测速，不能替代高延迟百流内存压力试验。

**延迟代价必须保留：** 原生四流下载的逐批 RTT 中位数，控制版约 100.5–100.9ms，候选约 204.1–226.2ms；单流下载候选约 114.5–127.3ms。四流数据不只是“缺少证据”，还实际提示了排队延迟增加。因此本次移植只证明可恢复吞吐，尚未证明同时优化延迟，不能直接改成默认或宣传全面优于旧版。下一阶段应在同路径比较对客户端待发送队列的有界控制，并同时约束吞吐、排队延迟和内存；验证之前不叠加生产调参。

候选二进制 SHA256：`d0265d1c919966173339f2d9314c76048608b6b099d0a2e9e9ee33053651bc61`；控制版为 `643c001b133410cefe7a769d0807c0eedf5a3f3635c7ef3d089058c8e9d2a259`。原生候选只验证 x86_64；官方 ARM64 兼容检查不能转写成该自编候选的 ARM64 验收。

源码与全部 JSON、SHA、CI 元数据、失败日志位于 [本轮证据](benchmarks/long-path-20261108/)。测试流量均在 GitHub 内部；本地下载的是结果文件，不下载压测内容。原生二进制只保留临时 CI 产物，未发布 Release、未加入安装器选项。产物过期必须按固定源码重建、重新核对摘要与验收，不得悄悄改用 latest。

## 实际维护、受限资源与空闲回收

[42469112057](https://github.com/bababoyi6/me/actions/runs/42469112057)，测试源码 `bf8e3aaa9d61ecaf558dae9afcc88882c79f2437`，始终使用上面同一份原生候选二进制摘要：

- 实际 systemd 非特权服务与生产 Python 维护适配器：首次安装、升级/重复升级、三个连接参数应用/重复/回退、API 权限、双 SNI 负载、SIGKILL 后重启、健康代理状态转换、回退至 balanced2、配置及 Token 原字节恢复、临时单元清理全部通过。这里调用内部适配器，不代表管理器公共命令已接受实验版本。进程重启观察约 1.1 秒，API 就绪另行确认；已有 TCP 会话仍需客户端重连。
- 整个负载环境限 **1 CPU、768MiB、无 swap**，私有 loopback 设置 25ms / 100Mbps；控制版、候选版分别完成 30/50/100 并发上传下载，合计 **720 条** 256KiB SHA/ACK 负载通过。模拟 DC 与客户端均使用 25 秒 IO 预算。
- 整个测试 cgroup 实测峰值 **180.84MiB**，OOM/oom_kill 均为 0。每核心 360 条流结束后等待两秒，FD 均 **14 → 14**；核心及代理进程退出，最终 cgroup 仅一个控制 PID。它是短时回收检查，不能替代持续高延迟百流内存与长期泄漏验收。
- 最新 root 回归 [42469116015](https://github.com/bababoyi6/me/actions/runs/42469116015)：**271 项、21.185 秒、无跳过**。测量、构建、维护、分析工具各自的 source commit 独立保留，不把不同提交合成同一次全套测试。

失败与修复也保留：`42467985415` 提权丢失 CI 标记，在安装前被保护拒绝；`42468090725` / `42468244608` 等 Release URL 返回 504，改为有界重试，并以固定资产 ID API 回退、原 SHA256 校验解决。官方包 ID 为 `695266457`，旧 balanced2 为 `672609415`；未替换资产或改为 latest。[官方兼容复验 42468557930](https://github.com/bababoyi6/me/actions/runs/42468557930) 的实际 systemd/双 WG/负载全部通过。

## 当前结论与尚未运行的项目
