# 临时 VPS 实测与 1.4.2 交付

本文是10月21日历史实测。最新1.5.0新安装默认核心、三角色验收及1Gbps预算对照见[新安装交付](FRESH-INSTALL-1.5.0.md)，不可用本文早期状态代替最新结论。

日期：2026-10-21。用户授权的一台临时荷兰 VPS：Ubuntu 22.04.5、Linux 5.15.0-161-generic、1 vCPU、MemTotal 979300 KiB、无 swap；CPU 型号显示 AMD EPYC 9354P。没有连接生产三机，没有获得用户网络和真实 Telegram 文件测速。

**结论：验证了兼容、安全维护和受控转发行为；没有证实生产 Telegram 大幅提速。** 不把临时单机内部的虚拟链路当成公网路线，也不把减少 HAProxy CPU 开销当成相同比例的下载加速。是否接近生产线路上限仍未知。

## 1. 测试边界与部署方式

测试工具从 Ubuntu 软件包下载后提取到私有实验目录，没有安装成系统服务。测试用 HAProxy 2.4.30、iperf3 3.9、wireguard-tools 1.0.20210914、ShellCheck 0.8；Python 为系统自带。为校验包含 `user haproxy` 的原始生成配置，测试进程用私有 NSS wrapper 将该名字映射到 nobody，未创建系统账号。

WG/限速/延迟/丢包只存在于三个独立 network namespace：模拟入口 A → 模拟路由 WAN → 模拟后端 B。没有修改主机公网 NIC、路由、防火墙、qdisc、SSH 或代理配置。netem 放在中间路由的两个出口，避免与发送端 TCP 的排队机制直接叠加；仅实验 veth 关闭 GRO/GSO/TSO，以按包施加丢包。端点命名空间使用 BBR，veth 使用 fq。WG MTU 1420、对端 AllowedIPs `/32`，入口主动、后端被动，密钥为随机临时值且不导出。实验 WG 未配置项目的额外 PSK，不能称为生产配置的完整复制；标准 WG 公钥认证与加密始终启用。

限速是每方向 100 Mbps 的实验链路预算，不能用于估算 VPS 公网带宽上限。所有监听均在私有命名空间或 loopback。退出清理自己创建的进程、namespace 和临时私钥；测试结果不包含服务器地址、登录信息、真实 Secret 或 WG 密钥。

## 2. 与 a update 一起生效的修改

管理器版本为 **1.4.2**；schema 5、协议 1.2.1、Telemt 3.5.5 保持不变。HAProxy/WG/Telemt 配置、unit、健康 agent、访问控制等 11 个核心生成函数与生产基线的 SHA256 一致。

| 修改 | 已验证问题与效果 | 适用范围 |
|---|---|---|
| 本机链接 API 固定直连 | 用合成 token 复现旧函数把认证头发送到环境代理；新函数忽略代理与 `.curlrc`，token 经 stdin 提供，curl 参数中没有认证头 | 管理器读取链接；不改已存在链接 |
| 失败信息收敛 | 链接等待失败不自动倾倒可能包含链接/Secret 的服务日志，改为简明中文提示 | 安装/维护失败输出 |
| 后续更新与回退自检限时 | 60 秒自检失败/超时保留当前管理器；状态查询 socket 增加 3 秒等待上限 | 管理操作，不重启数据服务 |
| CPU 与内存诊断修正 | busy 排除 steal，单独显示宿主抢占；增加 OOM、主缺页、换页计数的累计值与增量 | `a perf` 只读采样 |
| 测速结果质量校验 | 收发时段差大于 max(1秒,设定时长20%) 标为异常，保留数值但排除汇总；拒绝非有限/非正数值 | 按需使用的 iperf 工具，不是常驻服务 |

合成回归还验证了 CR/LF 认证头拒绝、引号/反斜杠保持、无效端口拒绝、日志不泄漏、旧版更新保持连接信息、失败回退与只清理实验自身资源。`a update` 仍只下载一个管理脚本；测试工具和测试依赖不会隐式安装到生产。

## 3. HAProxy 原生 Ubuntu 对照

逐轮原始数据：[40 次原生测试](benchmarks/vps-haproxy-2026-10-21.json)。1/4 流、上传/下载、普通复制/splice 各 5 轮，顺序交替，聚合限速 500 Mbps，每轮约 3 秒，全部校验 SHA256。使用项目已有的 loopback 测试程序；不包括 WG、Telemt 或公网。

| 场景 | 普通 Mbps 中位数 | splice Mbps 中位数 | 普通 CPU秒/GiB | splice CPU秒/GiB |
|---|---:|---:|---:|---:|
| 单流下载 | 499.701 | 499.670 | 1.088 | 0.859 |
| 单流上传 | 499.727 | 499.669 | 0.916 | 0.687 |
| 四流下载 | 498.865 | 499.004 | 0.974 | 0.744 |
| 四流上传 | 499.220 | 499.201 | 0.974 | 0.744 |

HAProxy 进程 CPU 中位成本下降约 **21%–25%**，吞吐基本不变。原始数据保留 P95/min/max 与实际分配管道观察值；5 轮 nearest-rank P95 等于最大值，CPU 按内核 tick 计时，样本较短。这里的 CPU 不包含其他进程及全部软中断开销。普通转发自身成本在这台机器上并未显示为 500 Mbps 的限制因素，不能将该百分比外推为 Telegram 提速。

首字节延迟也没有一致改善：部分 splice 组的最大延迟比普通组高，四流下载该指标的五轮 P95 分别约 3.407/2.768 ms。这些是合成后端响应，并非真实 Telegram 延迟。基于稳定性优先和单步更新边界，**splice 仍只留在实验中，不默认应用到生产**。

原生环境同时通过双 SNI、分片 ClientHello、PROXYv2、agent down→备用→主恢复、master/worker 重载中既有传输完整性检查。

另做[五分钟持续传输](benchmarks/vps-haproxy-soak.json)：两个长流各限速 10 Mbps，共实际接收 750,000,000 字节；另外 30 次 64 KiB 短探测均校验通过。约第 150 秒执行一次 master/worker 重载，两条既有长流完成且 SHA256 正确，总耗时 300.131 秒。这验证该环境下的持续传输与重载行为，不是生产长稳或真实 Telegram 保证，也没有证明实验 splice 的长期稳定性，因为长传采用原有普通复制配置。

## 4. WireGuard 与高延迟/丢包文件对照

### 无额外延迟的 iperf 探索

[逐轮数据](benchmarks/vps-wg-clean-2026-10-21.json)，100 Mbps 链路、每项 6 秒统计和 2 秒预热，3 轮，共 24 项。单连接 A→B 裸 TCP/WG 中位数为 95.572/91.457 Mbps，B→A 为 95.249/91.495 Mbps。

这是低负载下的有效载荷差异，包含封装开销；不能单凭约 4 Mbps 差值认定加密 CPU 是瓶颈。这批早期实验两端均设置了 endpoint/keepalive；随后按生产拓扑改为入口主动、后端被动。它不作为握手或高延迟故障的依据。

### 以实际完整字节和 SHA256 交叉验证

iperf 高延迟试验出现统计异常，见下一节，因此增加独立文件流：每项传输总计 18,750,000 字节，应用聚合限速 50 Mbps；单流/四流、双向各 3 轮，A/B 顺序交替。每个字节实际接收并校验摘要，吞吐以总字节除以整个并行组墙钟时间计算，包含客户端进程启动、连接、ClientHello 和收尾，不是只截取传输最快区间。它使用合成测试协议，不是 MTProto。

原始数据：[100ms 无丢包](benchmarks/vps-stream-rtt100.json)、[200ms 无丢包](benchmarks/vps-stream-rtt200.json)、[200ms 有丢包](benchmarks/vps-stream-lossy200.json)。每个场景 24 项，共 72 项，全部通过 SHA256。

| 100ms 无丢包场景 | 裸 TCP Mbps 中位数 | WG Mbps 中位数 |
|---|---:|---:|
| 单流 B→A 下载 | 46.097 | 46.127 |
| 单流 A→B 上传 | 44.202 | 44.307 |
| 四流 B→A 下载 | 44.147 | 43.687 |
| 四流 A→B 上传 | 42.402 | 41.903 |

这说明在该**有限速、有固定文件长度的合成条件**下，隧道并没有造成数量级下降；不能证明真实网络中 WG 没有 PMTU/UDP 线路问题，也不能估计极限吞吐。初始两份 stream 数据中的内存字段取测试结束快照，名称虽为 `minimum_available_memory_bytes`，不代表连续监测到的最低值；后续工具已改为 `available_memory_after_bytes`。

| 同为200ms RTT，WG 文件传输 | 无丢包 Mbps 中位数（min–max） | 每方向0.5%丢包 Mbps 中位数（min–max） |
|---|---:|---:|
| 单流 B→A 下载 | 38.413（38.380–38.628） | 27.520（27.031–29.701） |
| 单流 A→B 上传 | 35.250（34.927–35.302） | 26.274（25.271–27.513） |
| 四流 B→A 下载 | 41.447（41.317–41.695） | 40.160（11.460–40.161） |
| 四流 A→B 上传 | 39.154（39.153–39.156） | 36.920（34.112–37.568） |

在相同 RTT/限速/文件长度下增加丢包，单流吞吐明显下降，四流下载尾部也显著变差。样本只有三轮，随机丢包没有固定种子，不能估计稳定的长期 P95；三轮 nearest-rank P95 等于最大值，完整样本见原始文件。不能用单轮较高结果证明 WG 或某项优化更快；四个 TCP 流也不是四倍带宽，更不是可以透明合并一个 Telegram 连接的依据。这组对照支持先排查实际线路丢包，并不证明生产存在相同丢包。

### 临时机到五个固定健康检查目标

[25 次原始记录](benchmarks/vps-dc-connect.json)。每个地址 TCP/443 建连 5 次，每次 2 秒超时、间隔 0.1 秒，不发送 MTProto 或文件。序号按脚本 `TDH_TG_DC_IPV4` 顺序：149.154.175.50、149.154.167.51、149.154.175.100、149.154.167.91、149.154.171.5。

| 目标序号 | 成功次数 | TCP 建连中位数 ms | P95 ms |
|---|---:|---:|---:|
| 1 | 5/5 | 106.786 | 109.368 |
| 2 | 5/5 | 0.688 | 0.791 |
| 3 | 5/5 | 106.647 | 109.308 |
| 4 | 5/5 | 0.737 | 0.814 |
| 5 | 5/5 | 160.099 | 162.006 |

这里测到了真实公网的建连耗时差异，包含路径、远端处理与调度；没有下载有效速率或 ICMP 丢包数据，P95 也仅是五个样本的最大值。Telemt 的实际数据/CDN 地址可能不同，不能把这些探测地址当作全部会话路径。由此可推论：后端位置选择需要结合实际使用的 DC 与路由，不能因某个 DC 很近就认定该后端对所有 Telegram 使用都快；不会为此强制重定向用户 DC 或改变链接。

## 5. Telemt 官方二进制验证

[原始结果](benchmarks/vps-telemt-compatibility.json)。从官方固定 Release 下载 x86_64 GNU 包，下载后核对 SHA256：3.5.5 为 `2d5fb35b526f548bb6ffe7689cdf4f51f4108b97014be1b3b4186a58ab28d605`；3.5.14 为 `b10f86c6851f5c422a49d98deea55e8ef4aea7879605e59c1d4aa43c8f4c70ce`。

调用现有配置生成器，使用合成 Secret/入口地址，将监听和受信任 PROXY 来源替换为 loopback；进程以 nobody 运行，配置与工作目录权限单独设置，未注册系统服务。每版均完成两个 SNI 各 5 次顺序握手和总计 16 个并发握手，验证服务端 FakeTLS 响应 HMAC，不是只检查 TCP 端口打开。

| 指标 | 3.5.5 | 3.5.14 |
|---|---:|---:|
| 配置启动及 API 可用 | 通过 | 通过 |
| 合成链接匹配 / 配置不被改写 | 通过 | 通过 |
| 无认证 API / 只读写入状态 | 401 / 403 | 401 / 403 |
| HMAC 验证握手 | 26 次通过 | 26 次通过 |
| 顺序握手中位数 / P95 ms | 15.060 / 19.510 | 14.408 / 17.616 |
| 并发16握手中位数 / P95 ms | 14.758 / 22.783 | 16.507 / 18.987 |
| 探测后 RSS MiB | 15.254 | 15.387 |

每版仅启动一次、样本很少，FakeTLS 含刻意的响应时序模拟；上述差值不能证明新版更快。测试没有 MTProto 登录/Direct-DC 实际文件传输，没有负载下 Direct buffer 压力、2048 活跃连接或长时间内存曲线，也未验证 arm64 或完整 systemd 沙箱。结论是基础兼容通过，**保持生产 3.5.5，不把升级作为已验证加速**。

## 6. 测试中发现的异常与处理

[iperf 高延迟探索](benchmarks/vps-iperf-rtt100-exploratory.json)和[进一步保留的收发计时记录](benchmarks/vps-iperf-timing-anomaly.json)展示：发送端 5.999983 秒约 95.770 Mbps，接收端计时 16.213048 秒约 36.643 Mbps，而期间发送秒级区间持续约 95 Mbps。去掉预热也出现类似现象。没有充分证据把原因归结为单一 iperf bug、内核或网络排队，因此这批汇总不作为生产吞吐结论；工具增加时段质量判断，并用独立完整文件交叉验证。

初版新增实验客户端将极大的整数范围传给 argparse `choices`，格式生成消耗过多内存，实验 Python 进程被 SIGKILL；随后检查的主机 OOM 累计计数为 2，未将该累计值全部归因于此次测试。它属于**本次开发的实验工具问题**，不是原项目或生产故障。已改为常数大小的参数说明与数值边界检查，并增加 128 MiB 地址空间限制下的 CLI 回归；没有将该初版上传到生产管理脚本。测试输出保留累计 OOM 的事实，不用恢复后的空闲内存冒充从未出现压力。

原生 Ubuntu 的 Bash 语法、ShellCheck、内置自检、Python 编译、30 项自动回归与实际 HAProxy 行为检查均已通过，见[原生验证记录](benchmarks/vps-native-validation.txt)。测试涵盖旧 1.3.1 更新器从入口/backend1/backend2 一步升级的状态/链接/密钥逐字节保持，以及更新/回退失败时不替换当前管理器。GitHub Actions 也运行同一套常规检查；root namespace 实验与 Telemt 官方二进制探测需要单独显式运行，不在生产更新时执行。

[测试结束检查](benchmarks/vps-cleanup.json)确认实验 namespace、实验进程和临时 WG 私钥均为 0；TCP 监听仅剩原有 SSH22 和回环解析器53，OOM累计仍为2。该检查中的可用内存约639 MiB，是收尾快照，不是全程最低值。测试材料取回后仅删除本次专用实验目录，生产服务器始终没有连接或修改。

## 7. 升级、回退和剩余问题

候选 1.4.2 **发布到 main 后**，在生产入口和两个后端分别运行一次 `a update` 即取得新管理器，无需重新部署、重新生成链接或执行调参命令。当前本地候选尚未发布，更新只取得 main 已发布的内容。管理器不远程操作另外两台，不覆盖用户运行配置，不重载/重启数据服务。回退方式及原版 1.3.1 首次没有自动备份的边界见[审计手册第6节](PERFORMANCE.md#6-只运行-a-update-的兼容升级边界)。

新测试通过不代表稳定性已得到无限期保证，也不能称脚本“完美”。安全与诊断、维护路径有具体改善；生产速度是否能大幅提高，仍取决于用户→入口、入口→各后端、后端→实际 DC 三段证据。线路丢包、晚高峰拥塞或主机资源竞争若是瓶颈，改线路/地区或资源可能比 HAProxy 微调有效；需要同一运营商、时段和真实文件的交替对照来验证。

生产无需运行这些 root 实验工具。可选的低风险下一步仍是在真实下载/上传中执行 `a perf 5` 观察三台；报告不会上传。已有运行配置与连接信息保持不变。

## 8. 复现实验

仅在空闲临时 Linux 测试机准备已验证的二进制和依赖；`R` 必须是私有的 `tdh-audit-*` 专用目录。工具不安装依赖，不创建公网监听。下面不是生产升级步骤：

```bash
timeout 360 python3 tests/network_lab.py --root "$R" --label clean \
  --iperf "$IPERF" --wg "$WG" --rate-mbps 100 --seconds 6 --rounds 3
timeout 420 python3 tests/stream_matrix.py --root "$R" --profile rtt100 \
  --iperf "$IPERF" --wg "$WG"
timeout 420 python3 tests/stream_matrix.py --root "$R" --profile rtt200 \
  --iperf "$IPERF" --wg "$WG"
timeout 420 python3 tests/stream_matrix.py --root "$R" --profile lossy200 \
  --iperf "$IPERF" --wg "$WG"
timeout 360 python3 tests/lab.py --haproxy "$HAPROXY" --benchmark \
  --rate-mbps 500 --seconds 3 --rounds 5 --output "$R/results/haproxy.json"
timeout 90 python3 tests/telemt_probe.py --root "$R" --output "$R/results/telemt.json"
timeout 80 python3 tests/dc_probe.py --root "$R"
timeout 360 python3 tests/soak.py --haproxy "$HAPROXY" --output "$R/results/soak.json"
```

Telemt probe 需要 `$R/telemt-3.5.5/telemt` 和 `$R/telemt-3.5.14/telemt`，先核对上述官方资产校验值再提取。代理 API 的保护行为依据 [curl 官方配置/代理文档](https://curl.se/docs/manpage.html)，模拟网络的限制依据 [tc-netem 文档](https://man7.org/linux/man-pages/man8/tc-netem.8.html)。
