# 旧balanced2与原生17的满载对照计划

2026-11-09，事先登记。本轮重点是旧版基线及实验路由队列，不修改生产参数。最新固定正式版仍为3.5.17；此前所有官方高RTT退化、原生对慢控制组的RTT未达标及pilot负面结果保留，不改变旧分析规则。

## 新发现与问题

重新读取既有`42496474174/metrics.json`：同任务100ms四流下载，旧`3.5.5+tdh.balanced2`的TCP RTT中位数分别为209.45/223.32/207.80ms，吞吐159.25/153.35/155.18Mbps；官方17约84Mbps/100ms，官方17的auto实验约151–157Mbps/218–232ms。旧balanced2本身也排队，不能只把新优化版与较慢官方版对照就判断新版独有的延迟回归。

当前模型在私有中间路由区用netem同时模拟每向50ms传播延迟和200Mbps、10000包队列。上一pilot瓶颈积压可到约6MB。WG接口fq和客户端LOWAT未获得联合收益，下一步比较两核心在同一队列条件下的表现，并以有限队列进行机制检查。

## 固定条件与顺序

- 核心：历史Release的balanced2，归档SHA `b4fec3efd10288a9f211ad958337fa314a15486e72fd5c50ab870f22a19737e5`、ELF `5dc5d9b5ac43a0f12a402159e127b3b69e18ccb355c99b0322e73d870d907100`；原生17 balanced1 ELF `cd4c5ff500d956a8a7059e3e536ff139983a0c5897b4c410ea0e53c68a6cfa14`，固定构建run42495175073/source dec285fbdf5b42dd8be3e9e879bc0c2ad8994bc8，均实际核验。
- 路由条件：原始10000包与1500包两种队列；始终100ms/200Mbps、同一MTU1420，保持原有端点BBR/fq及WG策略。1500包约为该配置传播BDP同量级加余量，只是实验反事实，不是生产默认，也不声称精确等于真实路径队列。
- 四组：legacy-deep/native-deep/legacy-bounded/native-bounded。四轮Williams顺序，每组处于每位置一次，全部前后交叉顺序均衡。单/四下载32MiB，每轮反转单/四批次顺序，合计32批80计量流+64预热。
- 同一GitHub Ubuntu22.04 runner，真实HAProxy/WG/FakeTLS、独立客户端/DC进程、合成DC。核心一逻辑CPU，整个实验三CPU/1.5GiB、无swap、900秒上限；两个独立任务复验。只下载小型结果，本地不运行Linux测试、不访问VPS。
- 每个模型分别做上下行TCP容量对照，防止把改变模型容量当作核心收益。记录实际TCP RTT、独立ICMP p95、探测子进程CPU、路由qdisc积压/丢包、版本/配置SHA、完成数和清理。

## 新验收问题及规则

同一模型内，原生17相对旧balanced2的每一对吞吐均≥95%、TCP RTT中位数≤110%、路径ping p95≤110%，才标记`LEGACY_PARITY`。这验证旧版性能保持，不是超越旧版，也不改变此前80–200ms绝对RTT门槛的失败。

同一核心的队列机制检查，四流bounded相对deep每对吞吐≥95%，TCP RTT及ping p95均≤80%，才标记`MODEL_QUEUE_GAIN`；单流仅要求吞吐≥95%、两延迟≤110%，避免要求传播下限再降低20%。即使通过也仅说明该实验模型中队列影响，不能把限实验路由队列作为新核心修复或生产ISP队列解决方案。

前端/生成器+探测CPU≥70%、DC CPU≥70%、任一相关TCP容量对照<100Mbps、探测丢失均阻止收益/保持判定。缺批、版本/配置/队列漂移、未知二进制、少于5个ping、缺qdisc、错误/不完整DC计数、OOM或清理失败拒绝分析。两独立任务分别保留判定，不拼接最优批次，不回填缺测数据。

官方客户端、公网三机、1Gbps、24小时和抗封锁不在本实验结论范围。安装器继续保持原选择边界；性能门槛及产品默认尚需后续决策。
