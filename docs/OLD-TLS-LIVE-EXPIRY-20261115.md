# 旧核心 TLS 缓存运行中老化修复

2026-11-15。此分支从正式 `main` 单独创建，只带入旧核心 TLS 缓存补丁、隔离验证工具和专用 CI。正式管理器、安装器默认核心及冻结发布件未改动。先前 `security2` 的固定 SHA256 `72ab8e27f5a688264379eb76f5474ff791840615bcc06ed271f7e17afe84962d` 和验收记录仍属于旧二进制，不能套用于本次修复后的摘要。

旧候选只在启动读取磁盘文件时拒绝超过 72 小时的 profile。若进程持续运行且定期抓取失败，内存中的旧非默认 profile 会继续用于握手。修复把同一 72 小时上限用于运行中的读取、健康指标和快速重试筛选：过期时对客户端使用默认 profile，指标报告默认状态，该域会被重试；成功抓取的新 profile 重新生效。`security2.2` 再将下一次 profile 过期时间作为刷新任务的唤醒上限，避免进程睡在正常的 4–8 小时刷新周期里。过期 profile 不会让已经用完的快速重试额度无限重置。磁盘文件和内存中的旧值在成功刷新前不被原位改写。

验证顺序：固定 Rust 工具链重建并运行 TLS 模拟、缓存磁盘及运行中老化定向测试；取得新 SHA 后，在私有回环网络复核合成协议、两域 TLS 源恢复、停源冷加载和真实 systemd 生命周期/回退。工作流只手动触发，限制运行时间和资源，生成的证书与密钥只在 CI 临时目录。真实 Telegram 客户端与公网验证按用户决定暂缓，不能由这些 CI 代替。

## 100 ms 成对性能初筛

[CI 43719942306](https://github.com/bababoyi6/me/actions/runs/43719942306) 首轮在同一固定 SHA 上完成了 40 条计量传输，但单次上传 TCP 容量对照仅 78.58 Mbps，低于预设 100 Mbps 门槛，因此初筛未通过；该轮应用层上传随后达到 104.88–156.40 Mbps。为避免把一次容量波动当作稳定链路能力，工具改为同一 CI runner 连测三次并取中位数，仍保留 100 Mbps 门槛。

[CI 43721366145](https://github.com/bababoyi6/me/actions/runs/43721366145) 重新构建相同 `security2.2` SHA，在固定 100 ms / 200 Mbps 隔离 WireGuard 路径上，按 AB/BA 两轮比较已发布 `balanced2` 与候选的单流和四流双向吞吐及客户端 TCP RTT。上传、下载 TCP 容量对照中位数分别为 176.41、176.24 Mbps；上传三次原值为 176.41、176.49、78.22 Mbps。40 条计量传输全部通过摘要验证，吞吐逐对比值为 96.76%–103.06%，候选 RTT 相对基线最大增幅约 2.56%；3 CPU / 1.5 GiB / 无 swap 预算内峰值约 242.61 MiB，无 OOM，临时进程与网络命名空间均已清理。预设**相对性能初筛通过**，没有测出可重复的核心吞吐提升。

四流下载时，基线与候选的客户端 TCP 中位 RTT 约 220–226 ms，均超过 200 ms。该绝对带载延迟问题仍在，已有混合负载证据将主要积压指向隔离路径队列；本次初筛不能证明生产延迟达标，也不构成正式核心发布或部署批准。真实 Telegram 客户端、公网 TLS 源与公网容量验证按用户决定暂缓。本地原始回执见 `lab-control/evidence/2026-11-15-security2-performance/`。

## 固定核心的私有队列改善实验

为定位上述路径排队瓶颈，[CI 43723853307](https://github.com/bababoyi6/me/actions/runs/43723853307) 在同一固定 `security2.2` SHA 上比较原队列与双端 WireGuard 加密前 180 Mbps HTB/fq_codel。测试固定 100 ms / 200 Mbps、30 个合成逻辑连接、两轮 AB/BA，三次接收端本地 TCP 容量对照每方向约 183 Mbps。四批混合负载完整，无 OOM，峰值约 264.26 MiB，临时进程及命名空间均已清理。

两轮原队列的下载约 139.5 Mbps、上传约 34–35 Mbps，带载小消息 p95 约 298–299 ms、新连接 p95 约 1140–1147 ms。整形后下载约 134.7 Mbps，保留 96.56%–96.57%；上传约 72 Mbps，为原队列的 2.04–2.10 倍；小消息 p95 约 101–102 ms，新连接 p95 约 425–429 ms。两轮同时满足预先登记的下载/上传、消息/新连接延迟、绝对排队预算、CPU 和 RSS 联合门槛。这个结果确认在该隔离路径上，队列配置能明显改善固定候选的混合负载体验；它不是核心自身的吞吐提升，也不验证真实公网、双隧道共享容量或生产可用性。正式管理器与默认队列均未改动。原始记录见 `lab-control/evidence/2026-11-15-security2-queue/`。
