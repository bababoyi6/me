# 上行容量限制的单变量定位

## 执行前固定的假设和边界

此前100ms/200Mbps实验的容量对照反复为上行约69Mbps、下行约183Mbps。容量门槛仍是双向至少100Mbps；旧批次不改判，不重跑三核心大矩阵。

先区分iperf内部限速和网络本身。只在免费Ubuntu22.04标准CI、已有三命名空间和真实WireGuard上，固定100ms RTT、200Mbps双向netem、MTU1420、BBR、fq、CPU亲和性和系统默认缓冲。只改变iperf `-b200M` / `-b0`，上行ABBA、下行BAAB，各两次，共八次。每次2秒预热加6秒计量；总运行限180秒、3CPU、1.5GiB、零swap。约1.6GB以内的负载留在私有虚拟链路，不经过用户本地宽带。

保留完整iperf JSON、每秒两端TCP/socket内存及路由器队列快照，检查窗口、拥塞、重传与CPU。无Telemt编译，无核心、宿主sysctl或生产参数修改。工具完成不等于性能验收通过。

只有同方向两轮均显示取消内部限速消除容量不足，才认为该变量有因果证据；否则不采用。无论结果如何，不降低吞吐/延迟/样本门槛，不把旧失败改为通过。下一步只围绕观测到的限制处理，不扩大矩阵。

首次42581074585在新诊断工具的18秒单次截止处终止，清理通过，未形成有效对照。已传输约166MB、发送端交付速率约183Mbps，传输结束后控制通道有一个未读字节；不能依据未完成JSON判定容量。改回现有混合工具原本的25秒容量探测截止，并保留超时时的iperf输出和服务端等待点；整组上限相应改为300秒。八次原定对照、计量时长、网络参数和容量门槛不变。

## 容量观察与下一项最小筛选（执行前登记）

42581528010八次完成、OOM0、实验组峰值24.72MiB，进程和命名空间清理通过。上行两次200M汇总69.437/69.445Mbps；无限速两次69.698/183.092Mbps，不能认为取消内部限速修复问题。低读数的接收汇总时长16.12/16.15秒，发送汇总约6秒、183Mbps；逐秒发送记录及TCP交付速率也支持传输阶段约183Mbps。下行四次本地接收计量均约183.12Mbps/6秒。确证的是**计量窗口不一致**，尚未定位iperf内部为何迟滞，不能把发送速率直接替代接收速率。

容量工具改用每个方向的接收端作iperf客户端（均`-R`，U由B接收、D由A接收），继续6秒/2秒预热/200M，保存完整JSON；要求收发时长均在6秒±10%、收发字节差≤5%、速率可由字节/时长还原、本地接收逐秒字节和汇总一致。任一缺失直接拒绝，不选择发送端较高数字兜底。100Mbps门槛不变。补回归明确拒绝本次16秒反例。

容量校准通过才执行一次共享排队筛选：只用已发布balanced2，100ms/200Mbps/30逻辑连接，四对AB/BA、八批现有4下载+1上传、两条消息、四个新连接探针和19空闲连接。对比原WG noqueue与**两端加密前180Mbps HTB+fq_codel**，原路由netem延迟、带宽和10000持包限制不变。目的是在可见内层TCP流处排队，验证共享瓶颈的队首阻塞；不同于已经否决的WG fq单独添加或缩短netem队列。180Mbps仅适用于这条已知200Mbps实验路径，绝不能自动套到生产1Gbps端口或未知实际瓶颈。

四对均须：完整性/清理/OOM通过，U和D各不低于原95%，两种p95各≤原90%且≤各自空载+100ms，RSS和整组CPU秒各≤原110%，消息/新连接各至少20个满载样本，生成器/DC不受限。任一失败就不晋级、不继续换参数找赢家。通过才允许后续固定原生17候选确认；本次不改生产队列、管理命令或默认值，不引入守护进程。总实验780秒/3CPU/1.5GiB/零swap，无新核心编译。

下一步优先做**最小、默认关闭、带明确带宽输入与配置漂移拒绝的可回滚接入**：先确认真实角色/多WG接口共享总带宽的预算方式，再只补持久化、撤销及目标负载边界，避免把每条隧道都分配整机全部带宽。未验证前不提供让用户直接照抄的生产tc命令，也不自动按1Gbps端口标称值启用限速。本轮不再加测或调参寻找更好数字。
