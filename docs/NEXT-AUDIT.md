## 已确认与实际修复

| 问题 | 证据与影响 | 本分支措施 |
|---|---|---|
| namespace 名称全宿主固定，旧锁只覆盖实验目录 | 不同 `--root` 可同时检查到无 namespace，随后争用同名资源 | 安全打开 root 所有的全局互斥锁；拒绝软链接/硬链接/非普通锁文件及其他实验残留；回归验证不同目录互斥、锁释放、非归属私钥保留 |
| 健康后台线程可退出，旧 ready 标志没有有效期 | API JSON 为数组或 `data:null` 时 `.get` 可抛出未捕获异常；线程停止后，既有 True 标志可能持续被 agent 使用 | 先验证 JSON 类型、最多读取 16KiB；API/DC 分别记录单调时钟，5s/25s 过期即 down；异常输入和 stale 状态回归 |
| 就绪 API 的 HTTP 重定向可转发凭据 | 默认 urllib opener 会向跳转目标继续发送 Authorization；本地模拟302与独立接收端实际复现 bearer 转发 | 健康检查拒绝一切重定向，直接返回不健康；保留禁用环境代理，回归验证跳转目标收不到请求。触发前提是本地 API 返回重定向，不把它说成任意公网攻击者可直接利用 |
| DC 恢复只需一轮成功 | 故障期间间歇成功可能重新放行，下一轮再退出 | 保留全部五 DC 的严格要求与连续两轮失败；增加连续两轮成功才恢复。不把“一台 DC 故障”放松为健康，也不宣称已解决全部 DC 依赖的可用性取舍 |
| 路由断言依赖异步 DC 完成次数 | 本轮真实复现 `[1,1]` 误判：早先长流完成与后来备用连接重叠 | 所有 profile 统一读取 HAProxy 的连接分配计数；失败日志与修正后复验同时保留 |
| 旧实验只有进程级超时/内存采样 | 缺少实验进程树的硬内存/CPU/PID 预算；退出最后瞬间可能漏记 OOM | 新 supervisor 用临时 systemd cgroup 限制整个进程树，保留失败 unit 状态再回收；退出后再次核对宿主 OOM。工具不替代宿主容量管理 |
| 配对测试失败时缺少子进程日志 | 32 流首轮失败只留下非零退出，没有 trial 数据，不能追溯具体异常 | 新 A/B 驱动保存每个 worker 的独立日志；保留前一轮记录，不填补缺失测量、不产生不完整配对的提速比例 |
| 观测器对受限测试产生额外干扰 | 补日志后的32流失败定位到 `ss` 超过原有3s期限，而非已记录的传输校验失败 | 查询先按 Telemt 端口过滤，socket 采样从最多5Hz降为1Hz，保留3s期限；记录观测频率，不能把这一测试器修复当作历史核心回退已修复 |

安装器仍以单文件交付。`tools/health_agent.py` 通过 `tools/embed_health_agent.py` 嵌入；CI 检查两份内容严格一致。没有新增生产常驻代理或升级守护服务。服务权限、API token 文件、回环 API、WG agent 监听与原五 DC 地址均未改变。

健康状态仍通过原锁读取/写入，不改变线程共享状态的锁顺序；时间戳与标志在同一临界区更新，读取时也在锁内获取时钟，避免采样前后时序造成短暂误判。监控线程意外退出会让 agent 主进程退出，由已有 systemd Restart 策略重建，不额外增加常驻监控。过期只影响新连接健康判定，不强制断开现有会话。首次全 DC 就绪及恢复会多等待一轮（约 10s，另加探测时间）；原入口等待窗口仍覆盖这一范围。它改善的是错误健康状态与回切抖动的边界，不能保证所有故障下无中断。

## 32 流上传：证据与待定假设

历史同条件三轮中位数：flush-only 375.806Mbps，audit2 273.477Mbps，约 −27.23%。该负面结果继续保留，尚未证明已修复。

重新阅读原始逐轮数据发现：

- flush-only 上传的全机 busy 约 80.68–88.05%，audit2 约 74.13–75.92%，steal 均为 0。它们并非相同的满 CPU 状态，不能只凭“单核”认定 CPU 饱和就是完整根因。
- 两侧固定缓冲对照的 `rb/tb` 为 425,984 字节。audit2 客户端侧 `rb` 上限曾为 6,291,456，DC 侧 `tb` 最高 4,194,304，DC 侧 `rb` 为 131,072。**缓冲上限不是实际占用，不能直接相加当作 socket 已用内存**。
- 独立 observed 批次的上传：flush-only 369.974Mbps、客户端 namespace 重传增量 156；audit2 274.856Mbps、增量 2454；该轮 WAN 两个 netem 的 drops 增量都是 0。它不支持把回退简单归因为配置的 netem 丢包，也不能排除端点队列、重排、拥塞控制、调度或测量器竞争。
- Direct 用户态 copy budget 不限制内核 socket 内存；只比较 Telemt RSS 不足以否定 socket 内存压力。旧数据没有充分的进程组/内核记账对照，不能确证或排除竞争。

来源均在已有 `docs/benchmarks/native-1g-backpressure-three-rounds-*.json`、`native-1g-backpressure-observed-*.json` 和 `native-1g-backpressure-endpoints-*.json`。不同批次的数值不拼成一组新的中位数。

本轮新驱动按同一配置逐对交换顺序，先 1/4，再 8/16，最后有条件地进入 32。固定 CPU/内存预算改变了实验条件，因此**不能把新结果与历史无同等 cgroup 预算的数据直接计算提升比例**。详见本轮实验记录。

本分支保留 audit2 核心字节，不凭相关性添加 TCP 缓冲补丁或默认回退到损害高 RTT 单流的固定策略。下一步有价值的因果实验是：在相同安全预算下只改变 client/DC 单侧的 send 或 receive 策略，同时测完整性、上下行、窗口限制、实际 socket 记账与小消息竞争。按用户后续要求，运行验证只使用已授权荷兰机，逐级、顺序执行；本地只编辑、传输和保存源码/记录，不进行 Linux 实验或编译。先用有上限的直接 Netlink 观测减少测量器开销，再判断低配机是否具备进一步因果实验的余量。

## 上游复核

通过 [GitHub main API](https://api.github.com/repos/bababoyi6/me/branches/main) 和 [Telemt latest release API](https://api.github.com/repos/telemt/telemt/releases/latest) 重新核对。最新稳定版仍为 [3.5.14](https://github.com/telemt/telemt/releases/tag/3.5.14)，标签提交 `242946ba9cb4b868a7abaec07b94c55dad1ff6a7`，非 prerelease。

实际重新读取 `3.5.5..3.5.14` 的 socket、adaptive copy、配置与 API 变更：`src/transport/socket.rs` 没有变化，仍显式请求 256KiB；`adaptive_copy.rs` 的差异涉及 quota handle 传递，不能认定已替代本项目 flush 修复。配置/API 路径存在大量重构、文件系统安全、认证和生命周期相关变动，升级必须验证严格配置字段、账号/工作目录权限、双 SNI、API/agent、旧链接、重启要求及回退。

不因版本较新而默认自动升级；本轮没有生成或启用新的 3.5.14 定制核心。现有补丁、锁依赖、Rust 1.99.1 工具链与二进制摘要保持可追溯；“构建可重复执行”不等于已经证明不同构建机产物 bit-for-bit 一致。

## 威胁模型与安全边界

入口面临无认证探测、持有公开 Secret 的滥用者、慢连接/资源耗尽、协议指纹、入口单点故障和链路干扰。WireGuard 保护入口至后端的隧道，不能保护入口 IP 不被识别。半公开 Secret 泄露后，对方也能建立认证流；固定连接上限不是用户身份鉴别，更不是 30–100 用户容量证明。

本轮没有更改 TLS/MTProto 密钥派生、认证、密码算法、PROXYv2 信任来源、WG AllowedIPs 或 API 访问权限。没有用降低安全性换吞吐，也没有为追求“健康”而放松五 DC 要求。已有归档拒绝、摘要校验、私有文件权限、安装事务、回退和隐私回归继续执行。

未进行真实主动探测指纹、真实 GFW 干扰、官方客户端业务文件和不同运营商验证。抗封锁结论统一为 **NOT VERIFIED UNDER REAL CENSORSHIP CONDITIONS**。443、FakeTLS、知名 SNI 和双后端均不保证固定入口 IP 永久可用。

## 维护与发布门槛

`a update` 仍只更新管理器，`a update-rollback` 只回退管理器，不负责热迁移核心或新健康服务。已有节点不会因本分支源码变化自动更新 agent。核心事务工具继续保留摘要/身份/就绪失败回退能力，本轮未把它扩展成无中断生产升级命令。

新候选没有触碰 main 或发布 Release。后续发布前仍需完成当前源码三角色真实 systemd 安装与重启、完整官方客户端兼容、上下行与混合负载、资源预算内的 32 流调查、较长耐久与升级回退验收。历史三 guest 的 1.5.0 记录不能冒充本分支重新安装的结果。
