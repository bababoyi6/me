# 新旧核心配对测试方案与结果

2026-11-07。仅开发分支、GitHub 标准 Ubuntu 22.04 runner，无生产操作、不采购资源、不修改可见性、不恢复旧耐久实验。此文件先登记方法；结果必须以实际 CI JSON 补充。

## 固定对象与判据

复用 `FullLab`、`stable_acceptance`、生产配置生成器和现有真实 Fake TLS/obfuscated2/padded-intermediate 工具；固定官方 3.5.16 与发布的 3.5.5+tdh.balanced2 包/二进制双摘要。没有重编旧核心或将旧优化盲目移植到上游。

每个任务内串行配对，两版本都重新启动、相同四条小流预热、固定空闲间隔。六组中 A→B、B→A 各三组；第二个独立分配的 runner 反转顺序。同一任务内比较比率，不合并不同主机的绝对吞吐。

固定三种条件，每种都包含 30/50/100 并发上下行：

| 条件 | 配对数 / 每任务 | 数据量 / 连接 | 网络 |
|---|---:|---:|---|
| baseline | 6 | 256KiB | 私有 loopback netem delay 25ms / rate 100Mbps |
| sustained | 4 | 1MiB | 私有 loopback，无额外 qdisc 限速；单流发送器上限 125MB/s |
| impaired | 4 | 256KiB | 同 baseline 加 5ms 抖动、0.1% 丢包 |

多段 TCP 经过同一 loopback qdisc，delay 参数不是端到端 RTT；这些速度不是公网速度或 Telegram 文件速度。offline bootstrap 关闭外部 STUN/HTTP/TLS-front 采样，仅模拟 DC，不能据此评价真实伪装采样、官方客户端或抗封锁。

每个核心的全部线程限制在一个逻辑 CPU；负载生成器、模拟 DC 和 HAProxy 在另一逻辑 CPU，分别统计 CPU。整个任务 2 CPU / 1536MiB / 无 swap / 512 tasks / 1500 秒，工作流 30 分钟硬上限，两任务串行。实验预算包含模拟器，不能将其总内存当作后端 RSS。仅私有命名空间能修改 tc；没有默认路由，不传输公网测试数据。下载两包各最多 64MiB，原始结果为小型 JSON，保留 14 天并挑选脱敏证据入库。

所有配对需完整、配置策略哈希相同、摘要校验/协议尾部确认通过、子进程与临时目录清理通过。核心双方版本身份固定，模拟 DC 与客户端 IO 超时均为 25 秒。任一失败保留原结果，阻止该条件的速度结论，不重试覆盖。先报告成功率，再比较速度。

预登记工程门槛：每组新版吞吐比均 >1.05 且每组完成 p95 比均 <=1.10 才记为重复领先；每组吞吐比均 <0.95 才记为重复落后。其余为无明确差异或需回归审查；不是总体统计显著性或等效性证明。生成器/模拟 DC CPU 达到单核 70% 时标记测试端瓶颈，不把该结果当作核心极限。

## 已发现并修复的测试问题

旧 `stable_acceptance` 客户端等待 25 秒，而 `MockDc` 默认为 8 秒；此前 100 并发受限组完成时间接近八秒。现在对本验收明确设置双方 25 秒，保留旧批次原始数据。第一任务额外在旧核心上保持其余条件不变，依次记录 8 秒与 25 秒诊断；此诊断不参与性能比率。未得到观测前，不把旧版历史失败归因于核心或此超时。

原有 1.6 的成熟部署、双 SNI/WG、Direct-DC、回退逻辑继续保留。若 balanced2 某项优势跨两任务复现，再对照其 socket/buffer 补丁与新版源码，先查是否已被上游实现，再决定管理参数或可回退补丁；无证据不改核心。

无限速组模拟器/生成器 CPU 达到预定瓶颈门槛，不能据此评判核心吞吐极限；普通网络吞吐比率需与第二任务逐项合并复核，不拼接跨主机绝对速度。
