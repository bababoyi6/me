# 新旧核心配对测试方案与结果

2026-11-07 登记，2026-11-08 更新。仅开发分支、GitHub 标准 runner；正式比较为 Ubuntu 22.04，额外 Ubuntu 24.04 仅作环境诊断，不扩大生产系统支持。无生产操作、不采购资源、不修改可见性、不恢复旧耐久实验。

## 固定对象与判据

复用 `FullLab`、`stable_acceptance`、生产配置生成器和现有真实 Fake TLS/obfuscated2/padded-intermediate 工具；固定官方 3.5.16 与发布的 3.5.5+tdh.balanced2 包/二进制双摘要。没有重编旧核心或将旧优化盲目移植到上游。

每个任务内串行配对，两版本都重新启动、相同四条小流预热、固定空闲间隔。六组中 A→B、B→A 各三组；第二个独立分配的 runner 反转顺序。同一任务内比较比率，不合并不同主机的绝对吞吐。

固定三种条件，每种都包含 30/50/100 并发上下行：

| 条件 | 配对数 / 每任务 | 数据量 / 连接 | 网络 |
|---|---:|---:|---|
| baseline | 6 | 256KiB | 私有 loopback netem delay 25ms / rate 100Mbps |
| sustained | 4 | 1MiB | 私有 loopback，无额外 qdisc 限速；单流发送器上限 125MB/s |
| impaired | 4 | 256KiB | 同 baseline 加 5ms 抖动、0.1% 丢包 |

多段 TCP 经过同一 loopback qdisc，delay 参数不是端到端 RTT；这些速度不是公网速度或 Telegram 文件速度。offline bootstrap 关闭外部 STUN/HTTP/TLS-front 采样，仅模拟 DC，不能据此评价真实伪装采样、官方客户端或抗封锁。

每个核心的全部线程限制在一个逻辑 CPU；负载生成器、模拟 DC 和 HAProxy 在另一逻辑 CPU，分别统计 CPU。整个任务 2 CPU / 1536MiB / 无 swap / 512 tasks / 1500 秒，工作流 30 分钟硬上限，两任务串行。实验预算包含模拟器，不能将其总内存当作后端 RSS。仅私有命名空间能修改 tc；没有默认路由，不传输公网测试数据。下载两包各最多 64MiB，原始结果为小型 JSON，保留 14 天并挑选脱敏证据入库。

所有配对需完整、配置策略哈希相同、摘要校验/协议尾部确认通过、子进程与临时目录清理通过。核心双方版本身份固定，模拟 DC 与客户端 IO 超时均为 25 秒。任一失败保留原结果，阻止该条件的速度结论，不重试覆盖。先报告成功率，再比较速度。

预登记工程门槛：每组新版吞吐比均 >1.05 且每组完成 p95 比均 <=1.10 才记为重复领先；每组吞吐比均 <0.95 才记为重复落后。其余为无明确差异或需回归审查；不是总体统计显著性或等效性证明。生成器/模拟 DC CPU 达到单核 70% 时标记测试端瓶颈，不把该结果当作核心极限。

## 已发现并修复的测试问题

旧 `stable_acceptance` 客户端等待 25 秒，而 `MockDc` 默认为 8 秒；此前 100 并发受限组完成时间接近八秒。现在对本验收明确设置双方 25 秒，保留旧批次原始数据。第一任务额外在旧核心上保持其余条件不变，依次记录 8 秒与 25 秒诊断；此诊断不参与性能比率。未得到观测前，不把旧版历史失败归因于核心或此超时。

原有 1.6 的成熟部署、双 SNI/WG、Direct-DC、回退逻辑继续保留。若 balanced2 某项优势跨两任务复现，再对照其 socket/buffer 补丁与新版源码，先查是否已被上游实现，再决定管理参数或可回退补丁；无证据不改核心。

## 运行与证据

工作流 `.github/workflows/paired-performance.yml`，工具 `tests/paired_performance.py` / `tests/paired_analysis.py` / `tests/paired_report.py`。

正式批次 [42373634689](https://github.com/bababoyi6/me/actions/runs/42373634689)，固定测量代码 `80e9211073be3534cd5980b8d247533693ff59f8`，两任务完整结束但均因协议失败判 FAIL：普通网络组每任务每核心 2160 条传输全部通过；弱网组新核心各出现 4 次失败，共 8 次，旧核心对应组未失败。多数为 100 并发下载中的 payload EOF，另有一次上传 digest 阶段错误。此时不能宣布新版整体稳定性更优或完成生产放行。

第一任务的旧核心超时诊断中，模拟 DC 等待 8 秒时 100 下载全部失败、等待 25 秒时 100/100 通过。此前旧核心历史 100 下载失败不能作为新版稳定性优势证据。此结果只定位这个受限模拟场景，不解释所有旧版实际业务问题。

无限速组模拟器/生成器 CPU 达到预定瓶颈门槛，不能据此评判核心吞吐极限；普通网络吞吐比率需与第二任务逐项合并复核，不拼接跨主机绝对速度。

短程脱敏诊断 [42375124889](https://github.com/bababoyi6/me/actions/runs/42375124889) 中，旧核心 fast、新核心 fast、以及新核心非 fast 各两轮均通过，未复现上述中断，因此没有贸然修改生产 fast_mode。完整序列日志观察 [42375952065](https://github.com/bababoyi6/me/actions/runs/42375952065)、只在异常后采样且保持原构造/输出路径的观察 [42377323397](https://github.com/bababoyi6/me/actions/runs/42377323397) 也均未复现实际负载的中断。两者中的旧核心 8 秒反例是有意设置的超时诊断，不计入 25 秒实际负载。后续未复现不能覆盖最初两任务的 8 次失败。

首个 `a10ea15` 批次 42373447034 因提前发现指标文件为 root 私有权限、runner 无法可靠归档而取消；修正合成指标为可读文件后重跑。它没有计入性能结论，取消记录保留。

2026-11-08 收取 [双环境异常观察 42378866942](https://github.com/bababoyi6/me/actions/runs/42378866942)：目标 Ubuntu 22.04 新核心弱网 100 下载两次 `unexpected EOF`，实际收到的负载均为 **0 字节**，核心仍存活、模拟 DC 无错误且完成数少于提交数；Ubuntu 24.04 旧核心同条件出现一次相同的 0 字节关闭，新核心该任务无错误。两任务 OOM 增量均为 0。因此现有证据不能将同类故障认定为新版独有，也不能将普通网络整体通过包装成弱网通过；初始 8 次失败仍全部保留。下一步用弱网专用诊断记录失败连接的核心与 HAProxy 事件，不重复全量吞吐矩阵。

## 11 月 8 日：关闭原因与已实施修复

[逐连接日志 42447142628](https://github.com/bababoyi6/me/actions/runs/42447142628) 在 Ubuntu 22.04 / EPYC 9V45 上观察到新核心 4 次、旧核心 1 次关闭。每条日志均为 FakeTLS 成功、原生 MTProto 认证成功，然后连接模拟 DC 约 3.1 秒后 `Connection timeout`；HAProxy 记录后端关闭，负载尚未收到。它们不是进程崩溃、Secret/SNI 错误或传输中间丢失已确认数据。

两版上游默认总连接预算都是 3000ms；单次 `tg_connect` 为 10 秒、最多两次尝试，但首次等待已经耗尽总预算，不能保证真正得到第二次尝试。源码与配置参数审计后，采用显式每次 4 秒、最多两次、总预算 9000ms；正常成功路径无需额外等待。仅处理上游新连接，保留默认硬错误快速失败；严重故障下等待失败可能更长。

[确定性反例与修复验证 42447679131](https://github.com/bababoyi6/me/actions/runs/42447679131)，测量代码 `b9213873889a14edca26c5ababdcd06ea740a4ee`，真实发布二进制不变：

| 场景 | balanced2 | 3.5.16 |
|---|---|---|
| 只将 DC SYN 延迟 3500ms，上游原默认 | 3.244s 时 EOF，符合反例预期 | 3.199s 时 EOF，符合反例预期 |
| 同样延迟，采用有界重试策略 | 3.559s 完成负载、ACK 和摘要 | 3.565s 完成负载、ACK 和摘要 |
| 25ms / 5ms 抖动 / 0.1% 丢包 / 100Mbps，100 并发上下行各六轮 | 1200/1200 负载成功 | 1200/1200 负载成功 |

两边每次进程重启，测试后清理成功；确定性反例与弱网复验 OOM 增量为 0。对照日志任务与修复任务均为同型号 CPU，但不是同一台 VM；**不将其吞吐做跨主机比率**。确定性同任务两版控制反例和成功结果用于验证连接预算机制，2400 条弱网成功用于有限回归，不是长期零故障保证。

生产实现：新安装生成以上三个键；旧节点使用显式 `connect-refresh` / `connect-rollback` 事务，复用原备份、原子替换、服务就绪及中断恢复机制，并为配置目标保存 0640 与 UID/GID。仅修改缺失或上游默认参数，定制配置拒绝覆盖。核心升级仍原样保留配置，Secret/SNI 和用户链接保持。

初始两任务没有逐连接日志，不能逐条证明其全部 8 次失败原因；保留原 FAIL。该阶段修复覆盖已复现并有日志定位的连接预算问题；随后完整矩阵已补验，见下节。原普通网络的几个百分点差异不能因此升级为提速结论。

同批还补齐三 KVM 原生连接维护命令、配置漂移拒绝、反向回退、重复执行和重启，以及 267 项 root 回归。每批源码、分析工具与输入摘要独立记录，运行模板相同也不冒充同一提交的完整测试。

## 1.6 优点的复用与边界

11 月 8 日后续分离进程长链路实验已发现 100ms 单流下载退化线索，正在独立复验并构建原生 socket 移植候选，见 [LONG-PATH-20261108](LONG-PATH-20261108.md)。下表“暂不移植”记录的是此前矩阵阶段的结论；后续实验候选不等于生产默认已改变。

| 1.6 机制 | 当前处理 | 理由 |
|---|---|---|
| 单入口、双 SNI、双 WG、独立主备后端、Direct-DC / fast_mode | 保留 | 保持现有链接和部署模型，系统级验收已有证据 |
| BBR + fq 与小内存机器保守限额 | 保留，参数检查继续回归 | 本批不把 namespace 中的默认 cubic 测量当作 BBR 性能证明 |
| 安装、升级备份、管理器回退 | 复用并补充显式核心事务与排空恢复 | 沿用成熟流程，修复新核心权限与迁移要求 |
| balanced2 的读停顿时 flush | 目标核心已有相应实现 | 审计目标 `84e5b827a6619fb2e09ad3d09f253cdffe04bc2f` 的 `src/proxy/relay/adaptive_copy/copy.rs`，不重复叠加旧补丁 |
| balanced2 的 TCP 自动缓冲、低 RTT 接收策略、256KiB NOTSENT_LOWAT | 保留原补丁与旧核心回退，暂不移植到官方核心 | 目标 `src/transport/socket.rs` 仍有固定 256KiB 缓冲；不是等价实现，但本批没有证明这些差异导致了中断或有可重复收益 |

新核心发生中断不等于旧 socket 补丁就是修复；短程关闭 fast 的通过结果也不证明生产应关闭 fast。完整原因未确定前，不引入自编核心作为默认、不修改用户 Secret/SNI、不替换生产二进制。

## 可复验与测量限制

`paired-performance.yml` 及三个诊断工作流仅由 `workflow_dispatch` 显式启动，常规 PR 回归继续自动运行；没有定时重跑或长时耐久任务。可在开发分支手动启动，例如：

```sh
gh workflow run paired-performance.yml --ref dev/telemt-stable-compat-20261107
```

每次结果必须保留自己的提交、镜像、CPU、超时、资源预算和失败记录，不能为追求绿色覆盖旧结果。常规验收现已在首次失败时记录经过脱敏的原因、实际收到的负载字节数、耗时和核心进程状态，防止后续无法复现而丢失关键信息。

`handshake_ms` 只计客户端验证 FakeTLS ServerHello 并发出原生 nonce 的耗时，不包含服务端原生认证与 DC 可用确认；完整负载及尾部 ACK/SHA256 成功才证明本次合成传输完成。负载虽使用真实 FakeTLS/加密传输与真实二进制，其内容仍是模拟协议，不代表官方客户端 RPC、Telegram 文件吞吐、抗识别或抗封锁测试。
