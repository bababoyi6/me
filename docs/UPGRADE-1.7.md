# 1.7 安装、迁移与回退

候选目标：官方 Telemt **3.5.16**，固定 tag/commit/包及二进制 SHA256 见 [版本锁](telemt-stable-lock.json)。本分支未发布、未部署生产；`a update` 当前跟随远程 main，不能在候选分支尚未合并时假定它会下载 1.7。

## 安装与旧节点保护

新安装执行本分支审核后的 `telemt-dual-hop.sh`，仍按入口、backend1、backend2、回执注册的原流程部署。支持范围仍为 Ubuntu 22.04 / x86_64、ARM64。两架构均固定官方 3.5.16；ARM64 已在 Ubuntu 22.04.5 原生 runner 验证正式包安装、API 及双 SNI 协议传输，不代表完整 ARM 三系统或官方客户端验收。

```bash
sudo bash ./telemt-dual-hop.sh
```

下载途径必须是已审查的提交或交付包，并在执行前核对交付摘要。正式发布前不提供冒充已存在的 `v1.7.0` 下载 URL。原历史版本安装入口仍可用于各自历史部署；禁止把另一份安装命令当作运行中节点的重新初始化。

确实要保留旧 x86_64 核心的新安装，可显式选择：

```bash
sudo env TDH_NEW_INSTALL_CORE=balanced2 bash ./telemt-dual-hop.sh
sudo env TDH_NEW_INSTALL_CORE=audit2 bash ./telemt-dual-hop.sh
```

这是两个独立备选命令；不要在同一节点顺序执行。核心选择不接受任意 URL 或版本字符串。

已有节点只安装新版管理器时，仍保存 manager.previous，不修改核心、配置、密钥、隧道或用户链接。支持 schema 5 / 协议 1.2.1；历史 1.3.1 与 1.6.0 均使用此配置架构，但其管理器版本和核心不能混称为当前版本。原 `a update-rollback` 仅回退管理器。

## 滚动维护顺序

在入口安装并确认候选管理器版本后，先 `a diagnose` 确认另一后端可用。以 backend1 为例：

1. **入口**运行 `a backend-drain 1`。只有 backend2 在两条逻辑线路均为 UP 才允许排空；此操作停止向 backend1 分配新连接，不主动终止已有会话。
2. 查看 HAProxy `scur` 等待旧会话结束，或接受后端重启将断开这些会话。`--maintenance` 是操作者对维护条件的明确确认，后端不能独立证明入口已排空。
3. **backend1** 执行 `a core-upgrade --maintenance`，再执行 `a health-refresh --maintenance`。
4. **backend1** 执行 `a diagnose`；确认服务、隧道和协议抽检。健康代理冷启动通常至少需要三轮 DC 采样。
5. **入口**执行 `a backend-resume 1`，检查两条线路，完成后再以相同步骤维护 backend2。

不要同时排空两台。HAProxy 运行时 drain 不写入永久配置，入口重启或重载可能清除维护状态；维护窗口内不要重载/重启入口。没有新增跨节点公网管理 API、自动 SSH 或集群升级协调器。

## 核心事务实际做什么

下载只访问固定 HTTPS Release URL，并限制重定向协议、文件大小、连接和总超时。先验证包和解压二进制两个摘要，拒绝重复成员、符号链接、路径穿越及超限内容；候选 `--version` 以 Telemt 非特权身份执行。

运行候选 `healthcheck --mode ready 原配置`：用新版解析原严格配置并检查当前 API，不启动第二个代理进程。还核对现有 systemd MainPID 的 `/proc/PID/exe` 摘要，避免实际服务运行另一个核心却误报替换成功。

在停止服务前，私有备份包含旧二进制、状态文件、配置目录（含 API 令牌）、WG 密钥目录、当前 WG 配置、两个服务单元、存在的专用 drop-in 及旧核心源码许可材料。配置副本一律 0600、备份目录 0700；清单只包含路径、权限和摘要，不含凭据值。单次配置备份最多 128 文件/32MiB，最多保留 8 次快照，达到上限停止而不自动删除恢复资料。

旧核心备份、配置快照标识和事务阶段绑定在同一耐久日志；文件 fsync、原子替换并同步父目录。服务重启后要求 API 就绪且 MainPID 的实际核心摘要匹配。候选启动/就绪失败自动恢复旧二进制并重启旧服务；恢复失败如实报错并保留备份。

本次托管原生模板无需 TOML 重写，保持原文件字节，不增加新配置键，不重生成 Secret/SNI、加入信息或链接。3.5.8 起上游逐级以 `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` 打开配置父目录；旧 `/etc/telemt-dual-hop` 的 0710 权限会导致新核心报 Permission denied。新安装使用 root:telemt 0750。旧节点仅在明确核心维护升级时，将此目录 0710→0750；不改所有者、文件内容或子目录权限。专用服务组因此能列出顶层文件名，但 `state.env` 仍为 0600，WG 密钥目录及升级备份仍为 0700，服务账号不能读取它们。

迁移前在私有 `core-upgrade/config-access.json` 原子保存原模式、UID/GID、路径和原核心摘要；中断后重复运行按同一记录继续。预检失败恢复旧权限，核心回退至记录中的原二进制后恢复 0710；回退到仍需新版目录访问的核心时保留 0750。若中断发生在权限迁移后、核心事务日志创建前，`core-rollback --maintenance` 可仅恢复目录访问；原核心已被外部改动则拒绝并要求审查。定制模式、组、软链接或被改动的记录均不自动猜测转换。

上游也更严格拒绝配置/包含文件的软链接、硬链接或不安全布局；遇到定制 include、WEB、配额或非托管单元，应先单独审计。

## 快速回退与中断恢复

仍按“一次维护一个后端、入口先排空”执行：

```bash
a core-rollback --maintenance
a health-rollback --maintenance
```

两条命令分别回退核心和健康代理。核心回退要求受保护配置的摘要、权限及文件集合与该事务快照一致，且备份完整。配置被其他操作改动时停止，不静默覆盖新配置或用错误的旧快照回退。请在 root 私有目录中审查差异，再决定人工恢复；不要把整个备份目录上传给聊天、工单或公共 Git。

**若还要回退到 1.6 管理器，必须先在 1.7 管理器下完成核心回退并验证，再执行 `a update-rollback`。** 旧管理器不认识新核心维护命令，且其状态保存会重新写回 0710；不能在仍运行 3.5.16 时把管理器直接退到旧版后继续运维。管理器回退本身不回退核心或配置，这一顺序属于兼容路径的必要条件。

进程/终端在 prepared、switching 阶段消失后，先保留排空状态，再运行 `a core-rollback --maintenance` 恢复。重复同版本升级不替换原备份、不重启；重复已完成回退也是幂等的。升级前已经不健康的后端会在候选预检时被拒绝，不把升级当作盲目修复网络故障。

`a recover` 用于显式恢复后端 WG 与依赖服务；不能恢复丢失的密钥或迁移已经中断的 TCP 会话。1.7 候选不能绕过 `check_os` 自动改为其他生产发行版。
