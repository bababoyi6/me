# x86 双隧道空闲带宽回收

固定每条隧道 450 Mbps 能控制双路总预算，一路空闲时另一条仍只有半额。此前用共享 IFB 已验证空闲借用，但代理上传四轮都损失超过 5%。这次保留每个隧道现有的加密前 HTB 和 fq_codel，只调整各自类的速率，不使用 IFB 重注入。[共享 IFB 结果](SHARED-ENTRY-20261109.md) · [HTB 说明](https://man7.org/linux/man-pages/man8/tc-htb.8.html)

实验每方向总预算为 900 Mbps。两个隧道都活动时各 450 Mbps。一路连续三个采样周期低于 10 Mbps 且无排队，另一路积压或速率至少达到均分预算的 75% 时，切换为 875 / 25 Mbps。空闲线路恢复活动时立即回到均分。每次先降后升，调整过程中两路预算之和也不会超过 900 Mbps。上下行独立评估，实验在同一 runner 内读取各隧道发送端的计数。

CI 仅用两条私有 WireGuard 隧道和 iperf3，100 ms RTT、1 Gbps、4 CPU、2 GiB、240 秒上限。每方向分别比较固定均分与动态分配。第一条线路持续传输 24 秒，第二条约第 7 秒开始、持续 10 秒，两路始终在线。按接收端的完整一秒区间比较单路、并行和再次单路三个阶段。要求单路前后速率都至少提升 20%，并行时每条至少保留固定均分的 90%，新增流量后 2 秒内归还份额，并在第二条停止后再次借用。若未达标，保留结果。这个机制检查只回答带宽分配，后续代理验收才涉及小消息延迟及正式三机部署中的反馈协调。

[WireGuard 机制对照](https://github.com/bababoyi6/me/actions/runs/43569750034) 两方向均达标。单路空闲借用时接收端为 655–689 Mbps，固定均分约 379–381 Mbps。第二路加入后，0.91–1.35 秒恢复均分。并行时两路分别达到 369–390 Mbps。无 OOM，清理完成。

代理对照用正式 balanced2 和 HAProxy，继续使用相同拓扑和预算。比较单路 30 个连接和双路各 30 个连接，每条文件 128 MiB。单路及双路的上下行均需保留至少 95%，单路至少一个方向提高 20%。有效带载探测每类至少 20 条，p95 不超过固定组的 110%，相对空载增量至多 100 ms。分别保留完整性、预算时间线、CPU 和内存回执。单路和双路的对照顺序相反。本次只有一台 runner，跨机器协调尚不在此验收范围。

## 代理对照结果

| 指标 | 固定均分 | 动态分配 |
| --- | ---: | ---: |
| 单路下载 | 392.4 Mbps | 503.2 Mbps |
| 单路上传 | 251.9 Mbps | 236.6 Mbps |
| 单路带载小消息 p95 | 132.7 ms | 180.0 ms |
| 单路带载新连接 p95 | 537.3 ms | 674.2 ms |
| 双路合计下载 | 428.6 Mbps | 435.3 Mbps |
| 双路合计上传 | 110.5 Mbps | 116.0 Mbps |

单路下载增益达标。上传下降 6.1%，小消息和新连接 p95 分别升高 35.7% 和 25.5%，均超出相应的相对门槛。新连接 p95 相对空载增加 251 ms，也超过 100 ms 上限。单路有一组发送端在约 3.4 秒内先后切换六次，另一组在主要传输期间保持借用。切换记录只能定位控制行为，无法从这一次对照判断切换是否造成延迟升高。

双路有 19.7 秒以上的有效并行传输，两组的发送端全程维持 450 / 450 Mbps。动态组双路新连接 p95 相对空载增加 423–433 ms。固定组也增加 358–379 ms，说明即使预算维持均分，这组代理在同时满载时仍超出延迟上限。该现象不能归因于预算切换。[代理对照回执](https://github.com/bababoyi6/me/actions/runs/43570168222)

验收完整结束，清理通过，峰值内存约 618 MiB，无 OOM 或 cgroup CPU 限流。动态分配未通过代理门槛，仅保留 CI 实验和结果。正式配置继续使用现有策略。后续若优化代理满载延迟，先在固定预算下定位各段 TCP 发送队列与处理时间，再决定是否值得复测分配策略。

## 固定预算下的新连接分段

原代理对照已保存每个连接的传输就绪时刻。重算固定组双路负载，空载时传输就绪 p95 为 220–225 ms，带载为 391–394 ms。就绪到 SHA256 校验的阶段 p95 从约 202–203 ms 升到 419–450 ms。分别统计的 p95 来自不同样本，不能相加推算总 p95。

`gigabit-tunnel-diagnose` 只在固定预算下测一批双路负载。1 KiB 验证探针记录本地 TCP 建连、传输就绪、收到第一批有效载荷、读完整个载荷及收到 ACK 对应摘要的时刻。通过本地端口和从发起连接到传输就绪的时间窗口唯一关联 HAProxy 日志。分别保留 HAProxy 接收连接的等待估计、后端排队 `Tw`、后端 TCP 建连 `Tc`、所选后端及重试次数。剩余传输就绪时间包含首个协议往返和各端处理时间。ACK 和摘要是测试协议中的额外往返，单独计时。结果同时给出总耗时最慢十分之一内各阶段的中位数。[HAProxy 计时定义](https://docs.haproxy.org/2.4/configuration.html#8.4)

每约 250 ms 读取 HAProxy 和两个 Telemt 进程所属 socket 的 `TCP_INFO`，记录未发送量、RTT 与重传计数。并采样两端加密前队列、入口的共享上行整形及 WAN 模拟器的队列。观测只在实验命名空间内执行，不抓包。队列积压是采样瞬间的值，WAN 样本含传播持包，不能与 socket 未发送量相加作为某一连接的等待时间。[Linux TCP 统计定义](https://github.com/torvalds/linux/blob/master/include/uapi/linux/tcp.h)

两次诊断的负载及资源采样均完成。首轮因本地端口复用无法唯一关联日志。第二轮保存了完整的探针和 HAProxy 时间戳，但原关联规则假设 HAProxy 会在本地 TCP 建连后约 20 ms 内接收连接，满载时超出了这个窗口。用修正后的同一分析函数在 Windows 重放第二轮原始数据，完整匹配 40 条空载和 172 条带载探针，均选中预期后端、摘要通过、HAProxy 重试为零。两次 CI 都因关联规则记为失败，以下为第二轮离线重放结果。[首轮](https://github.com/bababoyi6/me/actions/runs/43572584786) · [补跑原始数据](https://github.com/bababoyi6/me/actions/runs/43572816923)

| 阶段 p95 | 空载 | 双路带载 |
| --- | ---: | ---: |
| 本地 TCP 建连 | <0.4 ms | 1.9–2.0 ms |
| 本地 TCP 建连后至 HAProxy 接收 | <1 ms | 51–56 ms |
| HAProxy 后端队列 `Tw` | 1 ms | 1 ms |
| HAProxy 到 Telemt 的 TCP 建连 `Tc` | 100 ms | 154–157 ms |
| 剩余传输就绪时间 | 118–119 ms | 169–174 ms |
| 传输就绪至首个载荷 | 102–103 ms | 209–213 ms |
| 读完 1 KiB 后的 ACK 和摘要往返 | 101 ms | 208–209 ms |
| 探针总耗时 | 421–423 ms | 750–762 ms |

固定预算下双路大文件有效重叠 15.85 秒，应用层下载和上传约 542 / 138 Mbps，10 条大文件校验通过。并行传输中，入口共享上行 TBF 的采样积压为零，共享下载 WAN 队列峰值约 5.67 MB，两个核心发往入口的大流 socket 未发送量峰值为 21.29 和 27.01 MB。所采队列无丢包，清理通过，无 OOM 或 cgroup CPU 限流。HAProxy 和两路客户端共用一个逻辑 CPU，该三进程合计采样 CPU p95 为单核的 66.6%，可能存在短时调度干扰。现有数据能定位延迟发生的阶段，无法单独量出 HAProxy 调度、网络模拟和核心处理各自的因果贡献。继续调整队列前，应先把压测客户端与入口进程分开，再对照入口接收延迟和跨隧道往返。

`gigabit-tunnel-affinity` 在同一 runner 上按「与客户端同核 → 移到模拟 DC 核 → 回到客户端核」执行三批相同负载。只移动 HAProxy，两个核心、客户端、DC 和网络参数保持固定。DC 与入口共用的是此前负载较轻的逻辑核。以两路接收延迟 p95 均比两次同客户端核的读数低至少 30% 作为可区分的改善。另报 `Tc`、首个载荷、摘要和总耗时及两向吞吐，检查改善是否同时延伸到跨隧道阶段。该对照针对 CI 的 CPU 布局。

| HAProxy 位置 | 下载 / 上传 Mbps | 两路接收等待 p95 | 两路后端建连 p95 | 两路首个载荷 p95 | 两路新连接总耗时 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 客户端核，首轮 | 564 / 148 | 83 / 79 ms | 153 / 153 ms | 207 / 218 ms | 802 / 770 ms |
| 模拟 DC 核 | 695 / 256 | 45 / 141 ms | 134 / 128 ms | 224 / 229 ms | 744 / 885 ms |
| 客户端核，恢复 | 559 / 166 | 86 / 125 ms | 162 / 150 ms | 199 / 208 ms | 731 / 851 ms |

三批 30 条大文件和 610 条纳入阶段分析的探针完成验证，双路文件有效重叠 12.24–15.25 秒，峰值约 834 MiB，无 OOM 或 cgroup CPU 限流，临时资源清理通过。移动 HAProxy 后，下载比两次对照高 23%–24%，上传高 54%–73%，后端 TCP 建连也缩短。第二路接收等待反而增加，未达到两路同时改善的判定条件。两条线路的首个载荷尾延迟也仍高于空载的约 102 ms。该对照表明 CI 的 CPU 放置会影响千兆模型的吞吐与阶段耗时，现有结果不足以用绑核解决尾延迟。[CPU 位置对照](https://github.com/bababoyi6/me/actions/runs/43573373141)

正式版本继续使用现有配置。本轮交付为可重放的阶段诊断与已验证的 CPU 对照。后续若要检验跨隧道尾延迟的网络成因，需要把共享带宽调度与传播延迟拆成独立模拟阶段，在吞吐可比的条件下做单因素对照。
