# 荷兰机续轮：轻量观测与32流边界

2026-10-23 续轮仍为测试候选。按用户要求，所有新增运行验证仅在授权荷兰 VPS 执行；本地只编辑、传输、校验和保存文件。没有运行本地 Linux 实验或编译，没有启动 CI、重装系统或访问美国生产机。Telemt 核心没有变化，历史32流约27%回退仍未修复。

## 代码交付

- 新增 `tests/kernel_observer.py`，以标准库 Netlink 读取 TCP socket 与 qdisc 统计，去掉每次采样启动 `ss`/`ip…tc` 的开销。只观察私有实验网络，socket 按 Telemt 持有的 inode 与地址筛选。
- 限定2秒目标期限、4MiB响应、4096条记录，检查内核发送方、序号、截断、中断、错误及属性边界；缺失可选字段保持缺失，不填零。进程描述符读取和结果解码也计入总耗时。
- qdisc 查询只进入三个固定实验 namespace，主线程执行并始终恢复原网络环境；恢复失败为致命错误。查询迟到或失败会保存已有传输记录、标记测量无效，并停止进一步 socket 查询。
- 新增受现有资源 supervisor 管理的 `--profile observer`，通过真实 `ss`/`tc` 和 socket 自身参数核对读数；更新故障注入回归。

没有添加生产常驻服务，也没有改动管理器、协议、认证、加密或默认核心策略。操作方法见[实验手册](SINGLE-VPS-LAB.md)。

实现提交为`18d9fd6`，后续证据提交只追加本次记录，不把失败判为通过。

## 大载荷失败揭示的限制

run `d3fc9075f973`计划32×8MiB、两对，但第一个flush对照就失败，audit2和后续轮次均未运行。32条流都未完成摘要确认，3次小探测失败；不能把已发送字节或qdisc字节计数当成文件完整传输，也不能据此计算auto退化比例。

该run出现40,544次`memory.high`事件，进程组采样最大166.14MiB；其MemoryMax约213.28MiB、MemoryHigh约159.96MiB。宿主可用内存采样最低约455.21MiB，OOM增量0。传输期间宿主CPU忙碌平均约15.94%，steal约0.02%；平均数不能排除瞬时调度停顿。client namespace重传增量46，两条WAN netem丢包增量均为0。内存回收/节流与失败同时出现，但尚未通过单因素实验证明根因。

v1仍获得前后qdisc与socket记录，不过两次socket采样耗时约5.497和2.625秒，原始`measurement_complete=true`暴露了只设置接收超时、未核对整次观测耗时的缺陷。[质量复核](benchmarks/next-continue-20261023/quality-review.json)明确判该测量无效，原始记录不改写。整个配对本来就失败，汇总没有输出提速比例。

随后v2增加返回后总耗时判定及迟到故障注入回归，并通过低负载核对和上述64MiB两对复验。**没有再运行256MiB或提高到1Gbps，也没有提高资源上限/超时来制造通过。** 去掉外部命令后，旧核心对照仍能在此受限场景失败，说明不能将此前失败全部归因于外部观测命令，更不能直接认定为audit2特有缺陷。
