# 单 VPS 优化候选：本轮验收、性能与资源记录

**结论：测试候选，部分实验室验收通过；不满足完整生产发布门槛。** 本轮交付了实际安全/可靠性修复、受限实验室与可复验工具；没有新增经过性能验收的 Rust 核心补丁。历史 32 流上传约 27% 回退仍为已知限制，不能标记已修复。

日期为 2026-10-23（北京时间）。原始记录使用 UTC。开发分支 `dev/single-vps-lab-20261023`，起点 `585f089e4cfe21fc2211275f609501c19c6437c8`。main 未修改，未推送、未发布 Release，三台美国生产节点未访问。

## 环境与源码身份

荷兰实验机实际为 Ubuntu 22.04.5 LTS、`5.15.0-161-generic`、x86_64、1 vCPU、956.35MiB RAM、无 Swap。初次只读预检可用内存 616.21MiB、磁盘剩余约 4.41GiB；监听为 DNS 53、SSH 22/222，未发现项目 namespace 或代理业务监听。没有重装系统、升级内核、安装完整虚拟机或改变宿主网络/SSH/防火墙配置。

使用既有经过校验的 HAProxy 2.4.30 与 WireGuard 工具，不在该机编译 Rust，不增加付费资源。Telemt 二进制身份：

| 对照 | SHA256 |
|---|---|
| flush-only `3.5.5+tdh.audit1` | `e0aa14b4032bbfa32fd5389e815371008a78aeae39ec099f9b850e2db3160582` |
| audit2 `3.5.5+tdh.audit2` | `2e5f864461be842dbca2ee8638f3b68327f56d5f1666ea0f2622a491b2ba75d1` |

audit2 与 1.5.0 默认 x86_64 核心**字节相同**。本轮单流对照收益不能写成“新版本比 1.5.0 又提速”。新源码的修复、威胁模型与上游评估见 [代码审计](NEXT-AUDIT.md)。各 run 的 manifest 保存实际命令、源码 SHA256、基准提交、dirty 标记与当时预算；测试期间源码分阶段演进，不能把较早 run 说成最终任意提交的整体回归。

## 1.5.0 与本候选

| 指标 | 1.5.0 基线 | 本候选 | 变化 | 验证环境 |
|---|---|---|---|---|
| 核心数据路径 | audit2 | 同一 audit2 | SAME_BINARY，无新增吞吐补丁 | 产物摘要复核 |
| 健康线程异常后旧 ready | 无有效期 | 有效期 + 主进程退出恢复 | 新增 fail-closed 与自动恢复边界 | LOCAL_UNIT_TEST |
| 就绪 API 302 | opener 可转发 Bearer | 拒绝重定向 | 本地双 HTTP 端点复现旧行为、新行为阻断 | LOCAL_UNIT_TEST |
| DC 恢复 | 一轮成功放行 | 连续两轮成功放行 | 降低反复回切机会，增加约一轮恢复等待 | LOCAL_UNIT_TEST |
| 不同目录同时创建同名 namespace | 目录锁不能互斥 | 全局安全锁 | 互斥与非归属文件保护通过 | LOCAL_UNIT_TEST |
| 32×8MiB/1Gbps 上传回退 | 已知约 −27% | 未修复，复验存在资源/观测缺口 | 不宣称性能通过 | 历史数据 + 本轮失败记录 |

没有单独执行两份相同 audit2 二进制的“新旧核心”吞吐比较。管理器/agent 的新变化也没有做真实 Telegram 业务流量 A/B，因此整版性能验收仍有缺口。

## 本轮上传对照

以下比较的是 **flush-only 与 audit2**，不是 1.5.0 与新核心。均为 `SINGLE_VPS_SYNTHETIC`：100ms 合成 RTT、100Mbps、原始 DC TCP 段、每项总有效载荷 16MiB、直接进入 Telemt。有效载荷不经过 WG，HAProxy 用于并行的小文件探测。CPUQuota=60%，整棵实验进程树的内存预算见每次 manifest。

每对顺序交替，先完成较小级别才增加负载。不同批次不混合计算中位数；1轮结果仅为探索性数据。

| 并发流 | 轮数 | flush-only 上传 Mbps | audit2 上传 Mbps | 差异 | 小文件探测中位 ms：flush / audit2 |
|---:|---:|---:|---:|---:|---:|
| 1 | 2 | 20.778 | 57.426 | +176.38% | 262.5 / 423.4 |
| 4 | 2 | 58.882 | 62.812 | +6.68% | 262.1 / 454.9 |
| 8 | 1 | 66.137 | 66.217 | +0.12% | 340.0 / 418.2 |
| 16 | 1 | 69.159 | 69.624 | +0.67% | 367.3 / 368.9 |
| 32 | 1 | 71.171 | 69.512 | **−2.33%** | 361.5 / 364.3 |

1/4 流来自 [两轮配对记录](benchmarks/next-lab-20261023/results/ab-1792760407751333751-summary.json)，8/16 来自 [一级探索记录](benchmarks/next-lab-20261023/results/ab-1792760719519385803-summary.json)，32 来自 [小载荷记录](benchmarks/next-lab-20261023/results/ab-1792762442844232179-summary.json)。32流每流仅 512KiB，不能代替历史每流 8MiB 的回退测试。

共14次有效 trial（7对）、132条上传流通过 SHA256，另有34次小文件探测，无探测失败。小文件统计包含新建连接与握手，样本数量与传输持续时间不同，不能当作既有聊天消息 P95 或严谨的显著性结果。**单流吞吐改善同时伴随部分小文件探测时延变差**，不能只展示吞吐正面数字。

成功小载荷试验的 Telemt RSS 采样约 24–29MiB；它不包括其他实验角色和所有内核 socket 内存。详细 socket 的 `rb/tb` 是限制值，不是已用内存。32小载荷的低开销模式没有详细 socket 样本，因此没有精确的全体 socket 内存峰值结论。

## 32×8MiB 的失败与停止依据

历史数据仍为 flush-only 375.806Mbps、audit2 273.477Mbps，约 −27.23%，详见 [根因审查](NEXT-AUDIT.md)。本轮尝试了每项256MiB、32流、1000Mbps 合成限额，但四次批次都未形成完整配对：

| run 后缀 | 观测模式 | 实际结果 |
|---|---|---|
| `8319849c39f3` | 旧详细观测 | 首个 flush worker 非零退出，未保存 trial；当时缺少子日志，原因不能追溯为确定结论 |
| `4e4cf47af485` | 旧详细观测 + 新日志 | `ss` 全量查询超过3s，停止后续负载 |
| `24b428940fcc` | 端口过滤、1Hz | `ss` 查询仍超过3s，停止后续负载 |
| `5b44553db6ad` | 关闭详细 socket 查询 | 到达负载后 `tc` 计数查询时超过3s；原工具未先保存 trial，不能倒推该轮具体完整性/吞吐 |

这些 run 的实验进程组采样最高约173–187.51MiB，多次触发 memory.high 回收；没有增加内存、Swap、重试或命令超时去强行通过。内存预算由同一公式动态产生，实际值逐 run 保存，不假设失败复验之间预算字节数完全相等。

失败时没有获得可用的新旧完整配对结果，**不能用零速补样本，也不能宣布已确认是 Telemt、socket 自动缓冲或 Tokio 的单一根因**。已经定位到受限环境的观测命令失败，尚未分离资源压力、测试器竞争与数据面退化的因果关系。

实际修复了日志丢失、全量高频观测以及后置观测失败丢弃 trial 的工具问题；最终工具会保留已经获得的传输结果并把 measurement 标为无效。后者由故障注入单元回归证明，本轮没有再重复高载荷32流试图制造通过。

## 拓扑、故障与受限耐久

`SINGLE_VPS_VIRTUAL_3NODE` 使用入口、后端A、后端B、独立模拟DC，以及WAN路由共五个 namespace。真实 HAProxy、WG+PSK、Telemt 都运行在同一物理宿主上；没有连接公网 Telegram DC。

首次 smoke 的异步 DC 完成计数造成路由断言误判，失败 run `0f565fe4aac1` 原样保留。改为 HAProxy 分配计数后，`0f4d2f261cad` smoke 通过。

最终受限长流 run `331704e9be65` 总计约359.5s，其中主下载为75,000,000字节、250,000字节/秒，约5分钟；[完整记录](benchmarks/next-lab-20261023/results/dualhop-native-auto-soak.json)有13次已校验传输，验证：

- 两个 SNI、分片 ClientHello、PROXYv2、双 WG/独立 PSK与双后端选择。
- agent down/up、备用接管新连接、主恢复，以及两次 HAProxy master/worker 重载期间既有长流保持。
- 真正停止并重新创建后端A Telemt进程，备用接管后恢复主路径。
- 只关闭入口 namespace 的第一条 WG 接口，恢复后重新选择主路径。

agent 为实验故障注入器，不能替代生产五 DC + API agent 的端到端安装验收。强制 splice 只用于兼容测试；本轮不据此更改生产默认值。故障切换不迁移已建立的 TCP 会话。5分钟低速长流不等于24小时长稳，更不是生产峰值负载。

## 资源报告

所有逻辑节点、模拟客户端和模拟 DC 共用同一个1核/约1GB宿主。实验 unit CPUQuota=60%、TasksMax=192、MemorySwapMax=0、最大600秒。根据当时可用内存，实际 MemoryMax 为206.73–245.29MiB，MemoryHigh为其3/4。宿主保留至少总内存的1/3。

| 场景 | 实验进程树内存采样最大 MiB | memory.high 事件最大值 | 结果 |
|---|---:|---:|---|
| 修正后 smoke | 159.54 | 314 | 通过 |
| 1/4流 A/B | 151.54 | 0 | 通过 |
| 8/16流探索 | 155.87 | 0 | 通过 |
| 32流大载荷的4个失败批次 | 173.00–187.51 | 7,316–12,842 | 观测/记录不足，未通过 |
| 完整拓扑低速长流 | 155.03 | 498 | 通过 |
| 32流小载荷 | 160.67 | 18 | 通过，不能外推大载荷 |

MemoryHigh 事件反映回收/节流，不等于 OOM。全程宿主 OOM kill 计数从0到0，结束时监听端口集合未变。由于5.15内核没有可用 `memory.peak`，这里是0.5秒采样最大值，不能称绝对峰值；CPUQuota也不能保证内核后台线程的全部 CPU 开销都受同样限制。

这些不是三个独立1GB后端的容量预算；也不能用成功32个合成连接推导32名活跃用户或100人满速传输。生产预算还包括系统、Telemt用户态、内核socket、WireGuard、HAProxy及突发余量，应以未来独立节点实测为准。

## 本地回归与构建

`LOCAL_UNIT_TEST`：代码提交 `dfb855d442f5dd36eccf9ca81a6ad4f00c99b6b2` 最终150项Python回归通过；Bash语法、ShellCheck、内置自检、核心/健康代理嵌入一致性检查通过。单独通过3项 Rust relay 回归（Rust 1.99.1、离线锁依赖、本地 Zig 链接器）及27个隔离安装中断/回滚场景，宿主账号文件未变。之后仅整理文档/证据及字节保留属性。不同类型检查不相加冒充一个“180项生产测试”。

本地完整日志保留在 [local/](benchmarks/next-lab-20261023/local/)。没有新增 Telemt 核心编译或上游全套构建，也没有执行任何 GitHub Actions 工作流或产生额外付费服务支出。
