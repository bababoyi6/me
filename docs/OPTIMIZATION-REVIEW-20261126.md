# Telemt Dual-Hop 优化审查

2026-11-26。以已发布的管理器 v1.7.3 和固定 x86_64 核心 `security2.2` 为基线。本轮管理器源码版本为 1.7.4，正式安装入口仍指向 v1.7.3。目标是保持 Telegram 官方客户端及现有链接兼容，同时降低负载下的等待、缩短故障恢复时间，并验证未经认证连接的外部行为。

## 优先级

| 优先级 | 发现 | 工程动作和放行证据 |
| --- | --- | --- |

## 外部实现中可借鉴的做法

- **Telemt 上游**保留了未经认证连接到真实 TLS 源的路径，并将外部指纹判断与客户端版本、源和路径关联。本项目应把普通 TLS 回落、认证后的 Telegram 协议成功率、错误恢复和外部特征分别记录。CI 能验证本机链路的协议边界。实际网络上的可辨识度需要独立观测。[Telemt FAQ](https://github.com/telemt/telemt/blob/main/docs/FAQ.en.md)
- **Outline 与 Shadowsocks 2022**关注认证、重放防御、失败行为及有界内存。**Tor obfs4**也明确记载了流量整形的性能取舍。这些项目的客户端握手不同，可借鉴其测试思路和资源预算。保持现有 MTProxy 链接可用的候选应通过真实客户端兼容性验证。[Outline 探测防御](https://github.com/OutlineFoundation/tunnel-server/blob/master/service/PROBES.md) · [Shadowsocks SIP022](https://github.com/shadowsocks/shadowsocks-org/blob/main/docs/doc/sip022.md) · [obfs4 规范](https://github.com/Yawning/obfs4/blob/master/doc/obfs4-spec.txt)
- **FQ-CoDel**在可见的内层数据流上组合公平队列和主动队列管理。对于两个 WireGuard 出口，逐接口限速不足以证明共享出口预算正确。需要同时观测内层和实际共享瓶颈。单隧道实验的 180 Mbps 只对应受控链路。[RFC 8290](https://www.rfc-editor.org/rfc/rfc8290.html) · [路径队列证据](PATH-CAPACITY-20261109.md)
- **HAProxy**提供 Unix Runtime API，排空等操作的状态在内存中。一次读写应有总时限，变更后应重新读取运行态。本项目的入口维护仍使用本机 Unix 套接字。[HAProxy Runtime API](https://www.haproxy.com/documentation/haproxy-runtime-api/)
- **USENIX 的 GFW 测量**分别记录被动分类、主动探测与 TLS 域名过滤。用这些证据定义待验证的风险，保留当前入口的实际可用性和网络差异作为独立指标。[加密流量实证](https://gfw.report/publications/usenixsecurity23/en/) · [GFWeb](https://www.usenix.org/system/files/usenixsecurity24-hoang.pdf)

## 本轮仓库改动

- `a perf` 在只读采样的两端各读取一次队列快照，报告每个接口下队列的发送字节、包、丢包、超限、重新入队的增量，以及采样结束时的 backlog 和 qlen。物理接口继续匿名化。接口或队列标识改变、快照缺失或计数下降时，对应增量为 `null`。两个快照无法检测期间所有瞬时积压或同标识重建。超限可表示整形计时，需与丢包计数分开读。
- HAProxy Runtime API 请求的 3 秒时限覆盖连接、发送和读取，零星响应无法延长管理锁占用。维持原有响应体大小上限与错误处理。
- 隔离回归使用管理器生成的 HAProxy SNI 和后端配置，把 TLS 源替换为本机证书夹具。测试验证未知 SNI 直接到 TLS 回落、两代理后端均下线时两个已配置 SNI 各自到对应回落、客户端证书验证和响应完整性。健康后端的分流、排空和恢复也沿用原回归。

## 下一轮证据

1. **双隧道共享队列。** 固定 ELF、带宽与 RTT，预登记原队列和候选的 AB/BA 顺序。分别记录双线路同时混合传输、单线路占用和单后端失效后的重新建连。在每个有效对照中，以基线吞吐保留至少 95% 为起始目标，检查消息与新连接 p95 同时改善，资源、连接失败和数据完整性一起判定。容量校准失败的批次记录为无效并保留原始数据。
2. **上游安全候选。** 先做提交级差异和依赖核对。固定候选后，检查原生 Fake TLS 认证、分片、配置和密钥权属、缓存过期与源恢复、超时、回退和资源上限。后续以同一 ELF 同时对照既有吞吐与尾延迟，避免将新旧候选结果混用。
3. **公网与真实客户端。** 在取得独立环境和客户端后，比较实际握手成功率、TTFB、长连接重连、低负载和带载分位数。在控源条件下观察普通 TLS 可用性，按网络和时间保留样本。现有隔离证据支持功能回归与性能定位。真实 Telegram 客户端、公网千兆、长期稳定性和抗封锁效果仍待验证。
