# 双 WireGuard 隧道的共享外层队列

## 试验设计

固定 `security2.2` x86_64 的正式安装归档及 ELF。使用两个真实 WireGuard 隧道、一个 HAProxy 入口、两个后端和单独的合成 DC 命名空间。双方向各有一个 100 Mbps 的共享入口链路，分支方向各有 50 ms 传播时延。客户端在入口命名空间内连接，排队位置是**入口和后端之间的加密外层链路**。这个模型中的公平调度能区分两条隧道，无法区分同一条隧道里的应用流。

把传播时延保留在独立的分支出接口。在共享链路的两个方向保留同一个 100 Mbps HTB 类，仅切换 1000 包的 `pfifo` 和 `fq_codel` 叶子队列。静态速率始终由一个共享类提供，另一条线路空闲时不设置固定的半速额度。对照顺序固定为 FIFO、FQ-CoDel、FQ-CoDel、FIFO。这里的 FIFO 是匹配限速和队列长度的实验对照。

## 判定门槛

- 两条隧道的空闲 ICMP RTT 均在 95–125 ms。以第一条隧道上的双向接收端 TCP 控制测量可用容量，方向各一次，在 60–105 Mbps 范围内才继续。容量原始数据保留。
- 每批运行已登记的 30 逻辑连接混合负载。每对分别检验上下行吞吐、带载消息与新连接 p95。再用同一线路各两个同向批量流测试单线占用，第一对使用线路 A，第二对使用线路 B。通过 HAProxy 分配计数核对路线和连接数。
- 每对的混合上下行和单线上下行吞吐均须保留至少 95%。消息及新连接 p95 均须降低至少 10%，每批各至少保留 20 个带载样本。混合负载整组 CPU 时间、采样峰值内存最多增加 10%。
- 每批标记主后端健康降级，在存活线路有并行下载时尝试原线路的五次新连接。核对存活后端分配与传输摘要，并记录健康摘除时间、各次重连耗时与下载重叠。重连样本量用于功能和描述性比较。
- 运行完成、内容校验和环境清理均须通过。整组限 3 CPU、1536 MiB、零 swap 和约 5 分钟，保存队列初末快照、失败和未达门槛的批次。人工 CI 选择 `security2-shared`。此实验不修改安装器或生产默认队列。

这个实验回答共享外层排队能否改善跨隧道竞争。后端分流前的应用级隔离、真实公网和长期稳定性需要独立证据。[单隧道内层整形结果](OLD-TLS-LIVE-EXPIRY-20261115.md) · [双隧道容量初筛](SECURITY2-EXTERNAL-QUALIFICATION-20261116.md)
