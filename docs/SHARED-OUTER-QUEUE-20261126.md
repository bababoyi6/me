# 双 WireGuard 隧道的共享外层队列

## 试验设计

固定 `security2.2` x86_64 的正式安装归档及 ELF。使用两个真实 WireGuard 隧道、一个 HAProxy 入口、两个后端和单独的合成 DC 命名空间。双方向各有一个 100 Mbps 的共享入口链路，分支方向各有 50 ms 传播时延。客户端在入口命名空间内连接，排队位置是**入口和后端之间的加密外层链路**。这个模型中的公平调度能区分两条隧道，无法区分同一条隧道里的应用流。

把传播时延保留在独立的分支出接口。在共享链路的两个方向保留同一个 100 Mbps HTB 类，仅切换 1000 包的 `pfifo` 和 `fq_codel` 叶子队列。静态速率始终由一个共享类提供，另一条线路空闲时不设置固定的半速额度。对照顺序固定为 FIFO、FQ-CoDel、FQ-CoDel、FIFO。这里的 FIFO 是匹配限速和队列长度的实验对照。

## 判定门槛

- 两条隧道的空闲 ICMP RTT 均在 95–125 ms。以第一条隧道上的双向接收端 TCP 控制测量可用容量，方向各一次，在 60–105 Mbps 范围内才继续。容量原始数据保留。
- 每批运行已登记的 30 逻辑连接混合负载。每对分别检验上下行吞吐、带载消息与新连接 p95。再用同一线路各两个同向批量流测试单线占用，第一对使用线路 A，第二对使用线路 B。通过 HAProxy 分配计数核对路线和连接数。
- 每对的混合上下行和单线上下行吞吐均须保留至少 95%。消息及新连接 p95 均须降低至少 10%，每批各至少保留 20 个带载样本。混合负载整组 CPU 时间、采样峰值内存最多增加 10%。
- 每批标记主后端健康降级，在存活线路有并行下载时尝试原线路的五次新连接。核对存活后端分配与传输摘要，并记录健康摘除时间、各次重连耗时与下载重叠。重连样本量用于功能和描述性比较。
- 运行完成、内容校验和环境清理均须通过。整组限 3 CPU、1536 MiB、零 swap 和约 5 分钟，保存队列初末快照、失败和未达门槛的批次。人工 CI 选择 `security2-shared`。此实验不修改安装器或生产默认队列。

这个实验回答共享外层排队能否改善跨隧道竞争。后端分流前的应用级隔离、真实公网和长期稳定性需要独立证据。[单隧道内层整形结果](OLD-TLS-LIVE-EXPIRY-20261115.md) · [双隧道容量初筛](SECURITY2-EXTERNAL-QUALIFICATION-20261116.md)

## 首次完整结果

固定提交 `6bad05b` 和 `security2.2` ELF。空闲隧道 RTT 约 100.4、100.3 ms，接收端 TCP 控制上行 91.27 Mbps、下行 78.66 Mbps。四批均完成，两个配对均通过预设门槛。下表始终按 FIFO → FQ-CoDel 展示实际数据，第二对的执行顺序相反。[完整 CI](https://github.com/bababoyi6/me/actions/runs/45830546962)

| 指标 | 第 1 对 | 第 2 对 |
| --- | ---: | ---: |
| 混合下载，Mbps | 66.59 → 77.34 | 77.22 → 77.48 |
| 混合上传，Mbps | 45.26 → 53.53 | 45.15 → 53.48 |
| 小消息 p95，ms | 219.8 → 101.2 | 220.1 → 101.6 |
| 新连接 p95，ms | 1744.5 → 427.0 | 1749.4 → 426.8 |
| 单线下载，Mbps | 56.46 → 54.95 | 56.36 → 53.91 |
| 单线上传，Mbps | 56.33 → 56.46 | 56.37 → 56.60 |

混合负载组 CPU 时间相对变化为 +3.8% 和 −2.3%，采样峰值内存为 +1.8% 和 −3.7%。四批共有 20 次故障后新连接均被路由到备用后端并通过内容校验。每批最大重连耗时由约 674–680 ms 降到约 450–453 ms，每批只有五次样本。两个合成 DC 无传输错误，OOM 计数无增量，临时命名空间、进程和密钥清理通过。

首轮容量校准通过后，`ip netns exec` 的挂载视图隐藏了 cgroup 文件，混合负载未开始。第二轮完成首个 FIFO 批次，随后内核拒绝用原句柄替换队列类型，性能对照不完整。分别改用仅进入网络命名空间及显式重建指定叶子队列，保持容量、负载和判定门槛。[首轮失败](https://github.com/bababoyi6/me/actions/runs/45829519767) · [第二轮失败](https://github.com/bababoyi6/me/actions/runs/45829980798)

## 独立复核和结论

另一台 GitHub runner 以相同提交、ELF 和门槛跑完四批，两个配对均通过。空闲隧道 RTT 约 100.2 ms，接收端 TCP 控制上行 91.56 Mbps、下行 78.58 Mbps。[独立复核 CI](https://github.com/bababoyi6/me/actions/runs/45831236902)

| 指标 | 第 1 对 | 第 2 对 |
| --- | ---: | ---: |
| 混合下载，Mbps | 76.68 → 78.40 | 77.44 → 76.96 |
| 混合上传，Mbps | 44.86 → 53.69 | 45.25 → 53.92 |
| 小消息 p95，ms | 465.1 → 101.2 | 458.1 → 100.5 |
| 新连接 p95，ms | 2563.2 → 423.1 | 1727.2 → 422.0 |
| 单线下载，Mbps | 56.54 → 54.55 | 55.39 → 55.71 |
| 单线上传，Mbps | 56.57 → 56.55 | 55.12 → 56.54 |

四对合计，混合上传提高 18.3%–19.7%，混合下载相对变化 −0.6%～+16.1%，单线下载保留 95.6%–100.6%。小消息 p95 下降 53.8%–78.2%，新连接 p95 下降 75.5%–83.5%。两次完整 CI 共 40 次故障后新连接全部通过路由和内容校验，两次均无 OOM 或清理残留。启用默认队列策略前需要独立验证两侧容量不对称、背景竞争、真实客户端与故障恢复窗口。

这项结果支持在下一轮实验保留共享外层 FQ-CoDel。收益适用于本模型中受控的 100 Mbps 队列。单独区分主动队列管理和跨隧道调度的贡献需要再设对照，上游实际瓶颈位置、跨机部署收益和公网容量仍待验证。
