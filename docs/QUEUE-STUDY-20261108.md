# 客户端排队与 WireGuard 调度实验计划

上一阶段 3.5.16 原生实验的四流下载 TCP RTT 中位数由约 101ms 升至 204–226ms；客户端 socket 待发送积压观测最大约 3.3MB。TCP RTT 是估计值，尚不能只凭它认定路径额外排队的来源。3.5.17 发布后源码审查确认整个 `src/transport` 未变化，仍需专门定位，不能宣称新版已经修复。

本轮先核验并兼容新正式版，再复用其同一份 `3.5.17+tdh.balanced1` 二进制做因果实验，不改变生产默认策略。实验组为原生基线、仅客户端 `TCP_NOTSENT_LOWAT=64KiB`、仅客户端 256KiB、仅私有 WireGuard 两端根 fq 调度。前两组使用仅供实验的预加载库，在私有监听端口既有 NODELAY 调用上附加限额，保持自动缓冲；不将预加载库用于部署。

使用 Ubuntu 22.04 GitHub runner、真实 HAProxy/WireGuard/Fake TLS、模拟 DC，固定 100ms、200Mbps、32MiB/流；每核心一逻辑 CPU，客户端/模拟 DC 分开。整个任务限制三核、1.5GiB、无 swap、900 秒。四组 Williams 顺序保证每组处于每个位置一次，任一候选相对基线前后各两次；每组单流/四流下载，轮换批次顺序。合计32批、80条计量流，另有64条双 SNI 预热。

原有 TCP RTT/缓冲/待发送计数、进程 CPU 与 SHA/ACK 继续保留；新增持续的私有 ICMP 探测与路由区 netem 队列快照。每次单个 ping 完成后再发下一个，停止时等待在途回复，避免人为制造末包丢失。记录原 WG qdisc/队列长度，非 fq 组恢复同一基线，不修改宿主 NIC、路由、全局网络或 VPS。

预登记联合门槛：四流每一对的吞吐均不低于基线95%，TCP RTT 中位数均不高于80%，独立路径 ping p95 均不高于105%。单流作为保护组：吞吐每对不低于95%、TCP RTT 不高于110%、路径 ping p95 不高于105%，不要求接近传播下限的单流也降低20%。两组同时符合才进入独立复验。CPU达到70%、TCP容量对照低于100Mbps、探测丢失均阻止“收益”结论。缺批、乱序、配置/版本/绑定漂移、失败或不足五个探测样本拒绝分析。本实验有意观察此前超出200ms门槛的现象，不修改此前已发布数据的判定规则。

若无组同时满足吞吐和延迟门槛，保留负面结果，不移植为默认；若有组满足，独立任务复验后再决定是否做原生实现或 WG 配置变更。官方客户端、真实公网三机、抗封锁、长期稳定均不在本轮证明范围。
