# balanced2 核心安装链与高延迟入口验证

本阶段补齐32流实验没有覆盖的安装和协议路径，不重新跑32流。默认脚本仍使用audit2，不发布正式Release，不访问生产节点。

## 核心安装链：在CI运行

`tools/candidate_bundle.py`只接受已核对的原生归档`bdb602274776fc6b29a5b2259a8d17bc2d3f65bcf974828c429c861cfb639dcb`，其中balanced2二进制为`5dc5d9b5ac43a0f12a402159e127b3b69e18ccb355c99b0322e73d870d907100`。不重新编译，不允许从CLI绕过摘要。

候选归档沿用现有安装器的六文件格式，保留上游许可、非官方修改说明、基础patch、构建来源和额外helper/构建器完整文本及摘要。`source.patch`只表示基础audit2补丁；全部额外修改保存在`build-provenance.json/source_kit`，避免把不完整的基础patch当成balanced2全部源码。

CI使用生产安装模块执行真实新装，在临时文件树中以`telemt`非root账户检查版本；验证已有目标拒绝、损坏包在落地前拒绝、源文件/许可保留。安装后的同一字节核心再以非root身份启动真实HAProxy与模拟DC，检查两个SNI、上传和下载各1KiB，总4KiB。没有生产部署或发布动作。

这覆盖核心安装模块、版本/摘要及协议兼容；不等同于公开Release下载、一条命令完成三台物理机器部署或真实Telegram客户端验收。

## 高延迟入口：待代码与CI完成后另行授权

新增`lab_runner --profile candidate --rtt 100`，只在私有网络命名空间运行真实HAProxy、WireGuard+PSK、两个balanced2后端和单独的模拟DC。入口到后端设100ms RTT，后端采样必须实际观测到两端client TCP RTT超过5ms，覆盖应保留接收自动调节的条件；记录接收缓冲，不假称直接读取了内核user-lock位。

单次检查包括两个域名分别上传/下载256KiB，以及3次4KiB的主备切换/恢复探测；合成有效载荷共1,060,864字节，发送前强制不超过2MiB。两条隧道都记录纯数字收发计数，要求双向且至少覆盖对应有效载荷；不保存WireGuard私钥或公钥输出。实际核心版本、SHA256、路由、两后端RTT和DC错误均须通过，缺观测不能标成功。

该profile运行上限180秒、CPU60%，沿用原动态MemoryMax和宿主预留、Swap0、Tasks192及运行中OOM/磁盘/输出保护。75%软节流默认不变；使用80%须针对本阶段再次得到明确批准。结束后回收命名空间、服务、临时目录和密钥。

当前只准备代码。没有执行新的VPS检查，也不声明高延迟入口或候选完整安装链已通过；CI与实测结果将在完成后追加原始证据。
