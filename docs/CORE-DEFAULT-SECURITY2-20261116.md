# x86_64 新安装默认核心切换至 security2.2

2026-11-16。管理器 1.7.3 将 x86_64 新安装默认核心固定为已正式发布的 `3.5.5+tdh.balanced2.security2.2`。原发布归档不能直接由管理器的受审计安装器接收，因此另以相同固定 ELF 制作六文件安装归档：归档 SHA256 为 `18e872f1ebe18ea13a5179a68e2824b6dcd2ce145682adede8b6b0955d22b8fe`，内部 ELF SHA256 仍为 `0b901711296707c23da7e8edda5509f108bd351f6e4b9c72f0f69a1b1fe71388`。下载失败或摘要不符时安装终止，不回退到其他构建。ARM 新安装仍使用官方核心；现有节点不会因安装管理器而自动换核心。

切换理由是旧核心 FakeTLS 特征缓存的有界原子落盘、运行中 72 小时过期与过期点唤醒修复。隔离协议、源恢复、系统升级与回退、两条 WireGuard 隧道的功能及公网 TLS 源抓取均已通过。100 ms 单隧道成对初筛中，候选相对 balanced2 的逐对吞吐为 96.76%–103.06%；共享 100 Mbps 双隧道 ABBA 中，下载和上传中位比为 `1.00023`、`0.99929`。这些数据支持性能基本持平，没有测出可重复的核心提速。[修复与性能证据](OLD-TLS-LIVE-EXPIRY-20261115.md) · [补充验证](SECURITY2-EXTERNAL-QUALIFICATION-20261116.md)

`balanced2`、官方核心和 `audit2` 仍可在 x86_64 新安装时显式选择。现有 x86_64 后端可在排空、确认备用健康后运行 `a core-security2 --maintenance`；`a core-baseline --maintenance` 可切回 balanced2，核心事务回退入口继续保留。切换核心会中断该后端现有 TCP 会话。默认队列和生产 VPS 未改。

真实 Telegram 客户端、三台生产公网链路、千兆容量、长期稳定性与抗封锁效果没有验证；aarch64 定制核心未构建。两版在四流下载时的客户端中位 RTT 都约 220–226 ms，现有绝对带载延迟瓶颈未解决。正式发布标签只表示资产固定且可下载，不等同于上述未覆盖场景的通过结论。
