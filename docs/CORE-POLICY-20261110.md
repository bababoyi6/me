# 新安装核心策略与速度保护

2026-11-10。本轮只解决现有默认策略与已知性能证据不一致的问题，不重跑已经完成/否决的吞吐矩阵。沿用独立开发分支和Draft PR #9，不发布、不合并、不访问VPS。

## 问题与最小修改

此前管理器虽已复现官方17在100ms单流下约21Mbps、已发布balanced2约105Mbps的差距，新x86安装仍默认官方17；README的“高延迟不推荐”没有约束实际默认。这会使普通新安装在没有主动选择时进入已知退化路径。

本轮恢复x86_64/amd64新安装默认`3.5.5+tdh.balanced2`，准确复用已发布包与二进制，不重新编译、不变更TCP、HAProxy、WG、Secret或链接。显式`TDH_NEW_INSTALL_CORE=official`继续使用锁定官方3.5.17；audit2仍为显式备选。ARM64默认继续官方17，绝不回退或误装x86核心。管理器更新不更换已安装核心，核心升级仍是显式维护事务，增加已知性能代价提示，不把兼容升级宣传为提速。

这恢复已发布稳定基线的选择，不是新版核心性能修复，也不能借用旧数据宣称本轮“新提速五倍”。原生17优化候选及队列实验均不因此自动放行。

## 安全和兼容边界

固定官方17仍是管理器的兼容目标和可选升级目标，tag/commit/双摘要锁不改。3.5.5源码已确认当前模板涉及的Bearer认证、API只读、可信PROXY来源及连接预算键存在；本轮再以实际二进制检查认证拒绝、只读拒绝、双SNI/Secret和完整数据。后端只监听WG，API回环，服务最小权限和管理器文件保护沿用。

旧核心不包含3.5.8之后全部文件/运行时加固，不能声称安全实现与新版完全等同。托管模板不允许外部不可信include/WEB/任意写API，root保护配置，已有正常balanced2生产本来也在使用此基线。定制配置/权限或需要新上游能力的环境需独立选择官方路径，不能用默认性能策略绕过安全审查。没有发现或声称已排除全部漏洞。

## 针对性验证登记

- 基础回归覆盖unset/空选择默认balanced2，显式官方/audit2、错误输入、既有核心不覆盖；新增ARM在unset/空值下仍请求准确官方ARM包的分支检查。
- 单次有界CI实际从公开固定安装URL下载balanced2/官方17并核对原固定SHA。复用已有`core_delivery_ci.install_case`调用真正的Bash下载/安装函数，仅curl边界映射到已下载的同一文件；ELF、包/二进制摘要、非root版本执行及许可留存均真实。该边界替换明确记录，不冒称未替换的全自动裸机安装。
- 两种选择各20条双SNI/Fake TLS上下行与小并发、实际Telemt/HAProxy+合成DC，数据SHA完整、API未认证401/只读写403、配置不变；腐坏包及既有目标各拒绝一次。CPU1/512MiB/无swap/180秒硬截止，实验结束临时文件/进程清理、OOM0。不比较吞吐或宣称100用户容量。
- 原生ARM保留一次独立功能检查；原有三KVM、官方系统长矩阵/排队实验本次不重复，因为它们不经过本轮默认下载选择函数，不能代替针对性检查。

实际结果按CI和准确source补齐。真实官方客户端、公网三VPS、1Gbps、24小时与抗封锁仍未验证。目录里的2026-11-07至11-10历史数据保留原版本与门槛，不改判。
